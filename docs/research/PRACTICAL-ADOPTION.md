# 실무에 적용하는 AI 개발 프로세스

> 초기 적용 제안이다. 팀 공통 기준·Electron 앱·병렬 개발·필수 설계 승인은 [현재 제품 설계](../design/PRODUCT-DESIGN.md)를 따른다. 이 문서의 다른 프로젝트 예시는 실제 개발 대상 지정이나 변경 승인이 아니다.

작성: 2026-09-17. 상태: 적용 제안. 실행 시스템을 설치하거나 실제 기능·테스트를 구현한 결과는 아니다.

## 1. 적용 범위

확정된 목표는 요구 정리부터 설계·구현·리뷰·웹 테스트까지 정형화하고, 중간 개입을 줄이는 것이다. 적용 저장소와 실행 제품은 아직 확정하지 않았다. 우선 기존 서비스의 기능 변경·버그 수정을 공통 작업으로 가정한다.

구체적인 예시는 현재 로컬에서 확인한 API 운영 허브 인계 명세(`api-monitoring-hub-poc/DEVELOPMENT_HANDOFF.md`, 이 저장소에 포함하지 않은 별도 프로젝트)를 사용한다. 해당 프로젝트 README는 설계 문서 단계라고 명시하고 있다. 이미 작성한 W01~W12 작업과 T01~T32 검증 기준을 재사용하며, 이 문서가 기존 제품 요구나 구현 범위를 변경하지는 않는다.

## 2. 일하는 방식

사용자는 업무 목적·반드시 지킬 조건·완료 결과를 전달한다. 에이전트는 기존 코드와 문서를 읽어 수용 기준을 채우고, 구현·검증·리뷰·수정을 진행한다. 사용자는 결과 화면과 근거를 확인한다. 제품 정책이 불명확한 경우에만 구체적인 선택지를 받아 결정한다.

| 단계 | 사용자가 할 일 | 에이전트와 실행 시스템이 할 일 | 다음 단계로 넘길 결과 |
|---|---|---|---|
| 요청 | 목표와 중요한 제약 전달 | 코드·문서 조사, 확정·가정·미정 분리 | 작업 명세 |
| 설계 | 결과를 바꾸는 제품 정책 결정 | 변경 범위·작업 순서·테스트 시나리오 정리 | 구현 계획과 완료 조건 |
| 구현 | 통상 개입 없음 | 서버·UI·관련 테스트 구현, 실패 수정 | 실행 가능한 변경 |
| 검증 | 누락된 외부 접근만 제공 | 고정 검사와 실제 브라우저 테스트 | 기준별 실행 증거 |
| 리뷰 | 정책상 필요한 최종 리뷰 | diff·명세·검증 결과를 대조하고 수정 | 검토 가능한 결과 패키지 |
| 전달 | 병합·배포 정책에 따라 판단 | 요약·실행 방법·남은 차단 사항 정리 | 최종 커밋, 테스트, 화면 |

요구사항이 충분하면 단계마다 승인을 받지 않는다. 일반적인 테스트 실패는 에이전트가 처리하며, 중요한 명세 변경과 위임 범위를 넘는 작업은 사용자에게 알린다.

## 3. 프로젝트에 한 번 준비할 것

| 준비물 | 구체적인 내용 | 준비가 됐다는 증거 |
|---|---|---|
| 프로젝트 지침 | 실행 명령, 구조, 금지된 동작, 상세 명세 위치를 짧은 AGENTS.md에 정리 | 새 세션이 문서만 읽고 작업 시작 |
| 개발 환경 | 의존성, 앱, 테스트용 저장소·계정·초기 데이터 준비 | 반복 초기화 후 같은 상태에서 실행 |
| 검증 명령 | 기존 빌드·타입·린트·API·웹 검사를 자동 실행 명령으로 연결 | 종료 코드와 실행 로그 수집 |
| 작업 단위 기록 | 목표, 완료 조건, 다음 행동, 실패 원인, 변경 버전 | 중단 뒤 진행 상황 복구 |
| 실행 정책 | 자동 수행 범위, 무진전 한도, 시간·비용 기준, 병합 정책 | 종료·차단 상태가 명확함 |

우선 사용하는 개발 도구에서 한 작업을 끝까지 검증한다. 세션 종료 후 자동 재시작, 이슈 대기열, 동시 실행은 별도 실행 관리자 단계에서 추가한다. 프롬프트와 문서만으로 프로세스 재시작까지 제공되지는 않는다.

## 4. API 운영 허브에 적용하는 첫 작업

**첫 작업 제안: 테스트 웹훅을 받아 저장하고, 범위별 목록·상세에서 확인하는 흐름.** 기존 명세의 해당 구현 작업과 검증 기준을 연결한다. 최초 실행은 전체 P0의 한 부분이며, 이 부분이 통과해도 P0 전체 완료로 표시하지 않는다.

입력 → 샘플 ACCESS 웹훅과 환경·리전·브랜드 범위.

처리 → 명세에 따른 검증·저장·중복 처리·범위 분리.

행동 → 조회 API와 목록·상세 화면에 실제 저장 결과 반영.

결과 추적 → 명세 항목, 테스트 ID, 실행 커밋, 로그, 브라우저 증거를 연결.

| 시나리오 | 검증 내용 | 주된 검증 계층 |
|---|---|---|
| 정상 수신 | 샘플 전송 후 목록·상세에서 같은 요청 확인 | API + 브라우저 |
| 중복 전송 | 명세상 동일 요청을 재전송해 중복 집계·표시 방지 | API + 브라우저 |
| 범위 분리 | KR/Kia와 US/Hyundai에 같은 ID를 넣어 혼합 여부 확인 | API + 브라우저 |
| 잘못된 입력 | 명세의 오류 응답, 잘못된 저장·집계 방지 | API |
| 재시작 | 저장 데이터가 재시작 후에도 조회됨 | 통합 + 브라우저 |

그다음 작업은 수신 대기·평가 상태 표시, 장애 사건과 조사 화면 등 기존 의존 순서대로 확장한다. 외부 연동은 모의 계약 검증과 실제 연결 검증을 따로 기록한다. 연결 정보가 없으면 해당 실제 검증만 차단하고 독립 구현은 계속한다.

## 5. 웹 테스트를 업무에 붙이는 방법

1. 요구사항을 읽을 때 정상·오류·권한·상태 변경 시나리오를 함께 작성한다.
2. 구현 중 브라우저로 실제 화면을 확인하고 반복할 동작을 테스트 코드로 남긴다.
3. 이후 변경에서는 저장된 테스트를 실행하고, 새 요구사항의 시나리오를 추가한다.
4. 실패를 제품 결함·테스트 결함·환경 문제로 나눠 수정한다.
5. 최종 변경 버전에서 필수 회귀 테스트를 실행한다. skip·미실행·불안정한 통과는 따로 보고한다.

예를 들어 목록 화면이 보인다는 검사에 그치지 않고, API로 입력한 요청이 올바른 범위에서 조회되는지, 상세 값이 맞는지, 새로고침 후에도 유지되는지를 확인한다. 테스트 기대값은 구현 화면의 현재 동작을 복사하지 않고 요구사항에서 가져온다.

웹 검증 도구 후보와 근거는 [조사 보고서 8~9절](RESEARCH-2026-09-17.md)에 있다. 도입할 도구·명령은 대상 저장소에서 실제 실행해 확정한다.

## 6. 실제로 받게 될 완료 보고

아래는 출력 형식 예시이며 실행 결과가 아니다.

```text
작업: 웹훅 수신과 목록·상세 조회
상태: 완료 / 부분 완료 / 차단
변경 버전: <commit>
구현한 내용: <서버·UI 변경 요약>
필수 기준: <통과 / 실패 / 미실행 수>
검증: <명령·로그·브라우저 trace 위치>
실제 연동: <확인한 연동>
모의 연동: <로컬에서 대체한 연동>
사용자가 확인할 화면: <주소·재현 순서>
필요한 결정: <있을 때만 선택지와 영향>
남은 작업: <전체 P0와 구분>
```

성공한 검사는 짧게 집계한다. 실패는 재현 방법, 기대값·실제값, 원인 가설, 시도한 수정, 필요한 입력을 자세히 남긴다.

## 7. 도입 순서와 합격 기준

| 순서 | 실제로 할 일 | 다음 단계로 넘어갈 조건 |
|---|---|---|
| 첫 기능 | 한 기능을 명세부터 실제 UI 검증까지 연결 | 단계별 추가 지시 없이 결과와 증거 생성 |
| 반복 사용 | 버그 수정과 두 번째 기능에 같은 절차 적용 | 사용자의 재설명·환경 수동 복구 감소 |
| 중단 복구 | 세션 종료와 서버 실패 후 재개 검증 | 진행 보존, 잘못된 성공 보고 없음 |
| 작업 대기열 | 작업 선택·재시도·종료를 실행 관리자로 자동화 | 맡긴 여러 작업을 상태에 따라 처리 |
| 운영 확대 | 독립 작업 병렬화, 오류 신호 연동 | 충돌·중복 없이 통합 검증 통과 |

최소한 기능당 사용자 개입 횟수, 검증된 결과까지의 시간, 재작업·회귀 발생을 기록한다. 기존 방식으로 처리한 유사 작업과 비교하며, 장시간 실행이나 코드량 자체를 성공 기준으로 삼지 않는다.

## 8. 다음 개발 작업에 사용할 요청문

다음은 작업을 맡길 때 사용하는 템플릿이다. 아래 지시문을 저장한 것만으로 실행기가 가동되지는 않는다.

```text
이 프로젝트의 기존 코드와 명세를 기준으로 다음 기능을 구현해줘.

목표: [업무상 달성할 결과]
완료 조건: [관찰할 수 있는 동작]
제외 범위: [이번에 하지 않을 일]

먼저 확정 요구사항·가정·미정 사항을 정리하고 코드에서 확인할 수 있는 것은
직접 조사해. 결과를 바꾸는 제품 정책만 질문하고, 독립적인 작업은 계속해.

설계 → 구현 → 관련 테스트 → 실제 브라우저 검증 → 리뷰와 수정을
연결해서 진행해. 단계마다 진행 허락을 요청하지 마.
기존 검증 정책이나 필수 기대값을 완화해서 통과시키지 마.

작업 상태와 다음 행동을 파일에 남겨 다음 세션이 이어받을 수 있게 해.
최종 변경 버전에서 실행한 검사, 실패·미실행 항목, 화면 증거를 보고해.
실제 연동과 모의 연동은 구분하고, 필수 검증이 남으면 완료로 표시하지 마.
병합·배포·외부 시스템 변경은 프로젝트의 기존 허용 범위를 따라.
```

API 운영 허브라면 기존 개발 요청문(`api-monitoring-hub-poc/DEVELOPMENT_REQUEST.md`, 별도 프로젝트)과 통합 명세가 제품 요구의 기준이다. 위 템플릿은 진행 방식만 보완하며 기존 계약을 대체하지 않는다.
