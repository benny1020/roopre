# 웹 시나리오 자동화 설계

작성: 2026-09-17. 상태: 기존 개발 자동화 설계의 확장안. 특정 웹 앱에 설치하거나 테스트를 실행한 상태는 아니다.

## 목표

사용자가 요구사항과 테스트할 앱을 연결하면 에이전트가 시나리오를 도출하고, 실행 가능한 테스트로 변환하고, 실제 브라우저에서 실행한다. 실패하면 원인을 분류하여 제품 코드·테스트·환경을 적절히 수정하고 재검증한다. 재현 가능한 테스트는 저장소에 남겨 이후 변경에서도 반복 실행한다.

'모든 시나리오 자동화'의 범위는 생성·실행·분석·유지보수 전 과정이다. 가능한 사용자 행동 전체를 빠짐없이 알아내거나 결함 부재를 증명한다는 뜻은 아니다. 명세별 검증 상태, 미검증 영역, 외부 서비스 제약을 보고한다.

## 기본 기술 구성 제안

| 요소 | 역할 |
|---|---|
| Playwright Test + TypeScript | 저장된 E2E 테스트 반복 실행, 브라우저 프로젝트, 리포트·trace |
| 브라우저 도구를 사용할 수 있는 에이전트 | 앱 탐색, 시나리오·테스트 생성, 실패 재현과 분석 |
| 기존 실행 관리자 | 작업 배정, 결과 수집, 재시도·예산·중단·재개 |
| 테스트용 앱·DB·외부 서비스 sandbox | 독립적이고 반복 가능한 테스트 환경 |

Playwright 공식 문서에는 planner, generator, healer 정의가 있다. 이를 기반으로 삼되 기존 실행 관리자와 연결하고 프로젝트별 완료 정책을 추가한다. 에이전트 정의를 설치했다고 환경·데이터·재시작·예산 관리까지 자동으로 해결되는 것은 아니다. 실행할 에이전트 제품과 Playwright 버전은 구현 시 고정하고 호환성을 확인한다.

매 실행마다 AI가 모든 버튼을 다시 추론하도록 하지 않는다. 시나리오 작성·탐색·실패 분석에 AI를 사용하고, 반복 검증은 저장된 테스트 코드로 실행한다. 예산을 정한 탐색 테스트를 보완적으로 수행한다.

## 개발 흐름과 연결

```text
요구사항·수용 기준 + 기존 시나리오 + 변경 코드
  → 시나리오 초안과 검증 누락 확인
  → 앱 실행·계정·데이터 준비
  → 실제 화면 탐색으로 조작 방법 확인
  → Playwright 테스트 생성·갱신
  → 실제 브라우저 실행
  → 실패 분류 → 제품/테스트/환경 수정 → 재실행
  → 독립 리뷰 → 최종 커밋에서 회귀 검증
  → 요구사항별 결과·trace·잔여 문제 전달
```

기대 동작은 명세와 제품 정책에서 도출한다. 실행 중인 앱은 실제 조작 방법과 현재 동작을 알려주는 자료다. 현재 버그를 정답으로 삼아 기대값을 생성하지 않는다. 새 기능이 아직 없다면 시나리오를 먼저 만들고 실행 테스트는 구현과 함께 구체화한다. 명세가 불명확하고 결과를 크게 바꾸는 경우에만 질문하며 독립 작업은 계속한다.

## 자동 생성할 시나리오 범위

| 관점 | 후보 시나리오 |
|---|---|
| 핵심 사용자 여정 | 가입·로그인·검색·생성·수정·삭제·완료까지 연결 |
| 입력·경계값 | 필수값 누락, 형식 오류, 길이 제한, 중복, 빈 결과 |
| 권한·세션 | 비로그인, 역할별 접근, 타 사용자 자원 접근, 만료·로그아웃 |
| 상태 유지 | 새로고침, 뒤로 가기, 직접 URL 진입, 필터·페이지 이동 |
| 실패와 복구 | API 오류, 지연, 연결 단절, 재시도, 중복 제출 |
| 화면·상호작용 | 지원하는 화면 크기, 모달·포커스, 긴 콘텐츠, 빈 화면 |
| 접근성 | 자동 검사에 더해 키보드 이동, 레이블, 포커스 확인 |
| 데이터 결과 | 저장 후 재조회, 삭제 후 접근, 중복 생성 방지 |

모든 기능에 모든 조합을 기계적으로 곱하지 않는다. 요구사항과 변경 위험에 따라 필수·보완 시나리오를 나누고 대표 조합을 선택한다. 테스트 수를 늘리는 것보다 중요한 동작의 검증 가능성이 우선이다.

## 시나리오 명세 예시

예시 기능: 일반 사용자가 본인의 프로필 이름을 수정한다. 제품 정책이 아래 조건과 일치한다는 가정의 설계 예시다.

```yaml
id: PROFILE-01
acceptance: [AC-PROFILE-SAVE]
priority: required
actor: 일반 사용자 A
preconditions:
  - 실행별로 독립적인 사용자 A와 초기 프로필 생성
  - 사용자 A로 로그인
steps:
  - 프로필 화면으로 이동
  - 이름을 새 값으로 변경
  - 저장
expected:
  - 성공 표시와 새 이름 확인
  - 새로고침 후에도 이름 유지
  - 프로필 조회 API에 새 이름 저장 확인
cleanup: 이 실행이 생성한 테스트 데이터 정리
```

연결 시나리오: 빈 이름 거부, 비로그인 접근 차단, 사용자 B의 프로필 변경 차단, 저장 API 실패 후 오류 표시와 재시도. 권한은 UI의 버튼 숨김뿐 아니라 API에서도 확인한다. 검증 방식은 실제 프로젝트의 계약에 맞춘다.

## 계정과 테스트 데이터 자동 준비

- 로컬 또는 격리된 테스트 배포 환경을 준비하고 서버 준비 상태를 확인한다.
- 역할별 테스트 계정을 생성하거나 전용 계정 풀을 할당한다. 병렬로 상태를 변경하는 테스트끼리 같은 계정·데이터를 공유하지 않는다.
- 가능한 경우 테스트용 API·fixture로 데이터를 준비한다. 가입·로그인 자체를 검사하는 테스트는 해당 UI 경로를 실제 실행한다.
- 인증 상태를 재사용하더라도 역할을 분리하고 만료 시 재생성한다. 인증 상태 파일은 비밀 정보로 취급하여 Git에 커밋하지 않는다.
- 시간·timezone·locale·seed를 필요한 범위에서 고정한다. 각 실행에 고유한 데이터 식별자를 부여한다.
- 정리는 실행이 생성한 데이터에만 한정한다. crash 후에도 해당 실행의 데이터를 식별해 정리할 수 있게 한다.
- 이메일·결제 등은 테스트 mailbox·공식 sandbox를 연결한다. 실제 결제나 실제 고객에게 발송되는 동작은 무인 테스트 경로에서 제외한다.
- OAuth·MFA 등은 제공자가 지원하는 테스트 수단과 사전 준비된 계정을 사용한다. 검증할 수 없는 구간은 명시한다. mock한 외부 연동이 실제 외부 서비스와 통합 검증되었다고 보고하지 않는다.

## 실행 단계와 소요 관리

| 시점 | 실행 범위 |
|---|---|
| 기능 구현 중 | 변경한 기능의 시나리오와 인접 회귀 테스트 |
| 작업 완료 전 | 핵심 사용자 여정과 해당 영역의 필수 테스트 |
| PR 준비·통합 완료 | 합의한 필수 회귀 묶음과 지원 환경 조합 |
| 정기 실행을 별도 설정한 경우 | 더 넓은 브라우저 조합, 탐색 테스트, 드문 경계 조건 |

초기에는 Chromium을 빠른 검증에 쓰고, 서비스 지원 정책에 따라 Firefox·WebKit을 필수 검증에 추가한다. 모바일 viewport·기기 에뮬레이션은 실제 기기 검증과 구분한다. 부하·성능 검증은 필요 시 별도 도구와 기준을 연결하며 기능 E2E 통과로 대신하지 않는다. 이 문서는 정기 실행을 생성하지 않는다.

## 실패 분류와 수정 정책

| 분류 | 자동 조치 |
|---|---|
| 제품 결함 | 재현과 증거를 구현자에게 전달, 제품 코드 수정, 회귀 테스트 유지 |
| 조작 대상·대기 방식의 테스트 결함 | 같은 행동·기대 결과를 유지하며 locator·대기 수정, 재검증 |
| 데이터·인증·환경 문제 | fixture·세션·서비스 상태 복구 후 재실행 |
| 명세 변경 | 변경 근거와 시나리오 차이를 검토한 뒤 테스트 갱신 |
| 간헐적 실패 | 최초 실패를 보존하고 제한 재실행, flaky로 별도 표시 |
| 원인 미확정 | 조사 기록과 증거 보존, 무진전 한도 후 차단, 다른 작업 계속 |

Playwright 공식 healer 문서는 기능이 깨졌다고 판단하면 테스트를 skip할 수도 있다고 설명한다. 우리 실행 관리자는 필수 테스트의 skip·미실행을 성공으로 인정하지 않는다. assertion 삭제, 임의의 기대값 완화, 무제한 timeout 증가, screenshot baseline 일괄 덮어쓰기로 실패를 숨기지 못하도록 변경 diff를 검토한다.

필수 여정의 flaky는 해결 전 완료 조건을 충족하지 못한 것으로 처리하는 것을 기본 제안으로 한다. 재실행 통과는 최초 성공과 구분한다. 격리한 테스트는 미검증 영역으로 계속 표시하고 은폐하지 않는다.

## 테스트 안정성과 시각 검증

- 사용자가 인식하는 role·label·text 또는 명시적 test ID를 우선 사용한다. 복잡한 CSS 경로와 임의의 고정 sleep 의존을 줄인다.
- 테스트는 서로 독립적으로 실행 가능하게 한다. 사용자 여정 하나의 단계는 하나의 테스트 안에서 연결할 수 있다.
- 테스트 결과에는 UI만 아니라 필요한 API 상태·데이터 지속성 검증을 연결한다. 내부 구현 세부사항을 과도하게 고정하지 않는다.
- visual regression은 OS·브라우저·폰트·viewport 등 실행 조건을 고정하고 불필요한 동적 영역만 제한적으로 마스킹한다.
- 최초 화면 baseline은 승인된 디자인 또는 별도 검토 근거와 연결한다. 이후 의도된 변경도 디자인 차이와 이유를 리뷰한다. 현재 화면을 매번 정답 이미지로 자동 교체하지 않는다.
- AI의 화면 평가는 레이아웃 문제나 어색함을 찾는 보조 수단이다. 기능 assertion·이미지 비교·접근성 검사와 함께 사용한다.
- 자동 접근성 검사는 발견할 수 있는 위반의 일부를 검사한다. 전체 접근성 적합성이나 실기기 사용성을 보장한다고 보고하지 않는다.

## 결과와 재개 기록

각 테스트 결과에 run ID, 시나리오 ID, 수용 기준 ID, 앱 커밋/배포 버전, 테스트 버전, 환경·브라우저, 시도 횟수, 상태, 실행 시간을 남긴다. 실패 시 trace·스크린샷·필요한 console/network/server 로그를 첨부한다. trace와 로그에는 토큰·개인정보가 포함될 수 있으므로 테스트 데이터 사용, 민감 헤더 제거, 접근 제한과 보관 기간을 적용한다.

사용자에게는 생성 수·실행 수·통과·실패·차단·skip·flaky를 분리해서 보여준다. 필수 수용 기준의 테스트가 생성되지 않았거나 실행되지 않으면 통과율 계산으로 가려지지 않도록 한다. 수정 전후 증거와 남은 미검증 영역을 함께 전달한다.

테스트 중 세션이 끊겨도 실행 관리자가 결과·데이터 소유권·다음 행동을 복구한다. 중간부터 이어 실행하면 상태가 불분명해지는 사용자 여정은 fixture부터 다시 준비하여 해당 테스트 단위로 재실행한다. 마지막 통합 커밋에서는 필수 회귀 검증을 수행한다.

## 첫 구현의 완료 조건

1. 실제 앱의 핵심 여정 하나에 대해 요구사항 → 시나리오 → 실행 테스트 → 결과 연결이 자동으로 이루어진다.
2. 로그인·데이터 준비와 정리가 사용자 개입 없이 반복 가능하다.
3. 의도적으로 만든 제품 버그를 잡고, 테스트를 약화하지 않은 채 제품 수정 후 통과한다.
4. locator 오류와 서버 오류를 구분해 적절한 대상을 수정한다.
5. 테스트 skip, 중단, flaky, 예산 소진을 정상 통과와 구분한다.
6. 최종 결과에 대상 버전, 수용 기준별 검증, 실패 증거와 미검증 영역이 표시된다.
