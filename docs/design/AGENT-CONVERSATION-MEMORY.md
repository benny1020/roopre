# 에이전트 작업실 · 개별 대화 · 지속 기억

작성: 2026-09-28. 설계: Astra. 구현: GPT-5.6 Terra. 독립 리뷰: Astra.

상태: **개별 대화·기억의 사용자 검토용 설계. 아직 해당 세부 설계의 본인 승인을 기록하지 않았다.** 앞서 제시한 선택형 작업실 보기는 사용자 `고고`로 진행하며, 새 데이터·실행 입력 계약은 이 문서로 검토한다. 제품 기능과 이 문서의 계획을 혼동하지 않는다.

## 1. 요구사항과 결정

확정 요구: 사진처럼 에이전트를 역할별 작업석에서 보고 개별적으로 대화한다. 대화/작업을 재개해도 기억을 유지한다. 여러 프로젝트의 표준 개발 흐름, 본인의 설계 승인, 병렬 단계, 독립 리뷰는 유지한다. 제품 코드 변경은 Terra, 설계/리뷰는 Astra가 맡는다.

추천 결정은 **루프리가 기억의 원본을 보관하고 모델에는 필요한 맥락만 전달**하는 것이다. CLI 세션 ID만 저장하거나 거대한 MEMORY.md 한 파일을 계속 붙이는 방식에 의존하지 않는다. 시작 단계에 외부 메모리 SaaS·벡터 DB·새 상주 서비스를 도입하지 않는다.

이번에 구현할 사용자 흐름:

1. 전역 관제의 선택형 `에이전트 작업실`에서 실제 에이전트를 선택한다.
2. `작업 / 대화 / 기억` 맥락에서 역할·프로젝트·기능을 확인하고 질문한다. 실행 전 에이전트는 프로젝트의 배치 목록에서 선택할 수 있다.
3. 답변과 함께 이번에 참조한 설계·실행·기억의 출처를 확인한다. 재시작해도 대화가 남는다.
4. 자동 대화 요약은 상담 맥락으로 이어지며, 팀 작업에 재사용할 내용은 `기억으로 저장`에서 범위와 원문을 확인한다.
5. 저장한 작업 기억은 해당 에이전트의 다음 승인된 실행 입력에 포함된다. 기존 승인에 영향을 주면 재리뷰 조건이 표시된다.

### 개별 대화와 실행 지시의 차이

현재 runner는 `claude --bare --no-session-persistence -p`를 컨테이너마다 실행한다. 이번 대화는 같은 에이전트의 역할과 허용된 작업 기록을 사용하는 **실행과 분리된 읽기 전용 상담**이다. UI에 이를 명시한다. 실행 중인 CLI에 메시지가 전달됐거나 코드를 바꿨다고 표현하지 않는다.

대화에서 작업 방향을 바꾸려면 기존 설계/지침 편집으로 이동하거나 검토한 기억을 저장한다. 모델 답변은 승인·취소·코드 수정·머지를 실행할 수 없다. 실시간 실행 도중 지시 주입은 별도 세션/도구 수명주기 변경이 필요하므로 후속 설계다. 이 제한을 숨긴 가짜 `전달 완료` 상태를 만들지 않는다.

## 2. UI와 에이전트 정체성

작업실은 기존 프로젝트 흐름/역할 맵을 유지하는 선택형 보기다. 작은 아바타·작업석·이름·상태만 사용한다. 실제 작업 중인 인스턴스를 강조하며, 예정 배치/종료 기록/오래된 상태는 구분한다. 캐릭터가 움직이는 것만으로 실제 진행을 표현하지 않는다. 목록 보기와 동일한 상태 판정·상세 이동을 쓴다.

장기 정체성은 `workspace + projectId + agentDefinitionId`다. 이름 변경이나 definition revision 증가로 대화/기억이 사라지지 않는다. 같은 전역 정의를 다른 프로젝트가 쓰더라도 기억은 공유되지 않는다. 한 프로젝트의 같은 정의가 여러 단계에 배치되면 현재 assignment/stage를 대화 상단에 명시한다.

실행 정체성은 기존 `runId + attempt + executionId`다. 실행 당시 agent ID는 해당 run의 resolved harness와 assignment ID로 검증하며 이름으로 추정하지 않는다. 과거 실행 카드를 선택하면 당시 기록은 유지한다. 상담에 현재 정의/연결을 쓰는 경우 현재 설정 revision과 참조 중인 과거 실행을 각각 표시한다. 삭제/보관된 에이전트의 기록은 열람하되 신규 모델 호출을 차단한다.

대화 thread는 `workspace/project/agent/feature` 범위로 하나를 재사용하며 feature가 없는 프로젝트 상담도 별도 thread다. 전역 agent 전체 대화로 프로젝트 자료를 섞지 않는다. 범위 전환은 입력 초안·선택 기억·스크롤을 구분해서 보존하고 이전 응답이 새 thread에 나타나지 않게 한다.

feature 없는 범위는 정규화된 sentinel/비어 있지 않은 scope key로 저장해 SQL NULL unique 예외로 중복 thread가 생기지 않게 한다. turn에는 선택 assignment/stage·현재 agent revision·harness hash·참조하는 실행 revision을 고정한다. 프로젝트 상담은 프로젝트 단위 기억만, 기능 상담/실행은 같은 프로젝트의 공통 기억과 해당 기능 기억만 읽는다. 다른 기능 전용 기억은 제외한다.

작업실에서 클릭 → 상세 Inspector → 대화 탭의 좁은 상담 패널 순서다. 채팅이 개발 작업 공간 전체를 대체하지 않는다. 1024px에서는 패널을 아래/전용 상세로 전환한다. 단계 상태·필요한 승인·검증 근거가 대화보다 우선한다. 실제 에이전트가 없을 때는 배치 관리로 안내하고 가짜 실행을 만들지 않는다.

## 3. 기억의 네 층

| 층              | 보관/사용                                                             | 신뢰·범위                                                                   |
| --------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 원문 대화       | 메시지·시각·thread·응답 상태·요청 ID를 PostgreSQL에 영속 저장         | 사용자/모델 출처를 구분, 모델 답변은 검증된 사실 아님                       |
| 대화 요약       | 완료된 답변과 함께 갱신하는 짧은 구조화 요약, 포함한 메시지 경계/버전 | 자동 생성·확인 전, 읽기 전용 상담에만 사용                                  |
| 작업 체크포인트 | 기존 run/attempt/tree/정책/검사/agent output과 중단·재개 상태 참조    | 실행 기록이 원본, 성공과 실패를 구분, 완료 주장은 검사 근거와 별개          |
| 장기 작업 기억  | 사용자 확인한 결정/주의점/학습 내용과 출처·revision                   | 해당 프로젝트+에이전트, 선택적으로 특정 기능만; 승인된 실행에 고정해서 사용 |

전역/프로젝트/단계/에이전트 지침은 기존 harness가 원본이다. 기억이 지침이나 승인 기준을 덮어쓰지 않는다. 팀 전체에 적용할 컨벤션은 기억이 아니라 기존 표준/지침 편집으로 안내한다.

### 자동 유지와 제한

원문은 매 턴 저장한다. 컨텍스트는 **현재 질문과 필수 harness를 먼저 확보**한 뒤 최근 대화, 유효한 장기 기억, 작업 체크포인트, 상담 요약, 관련 과거 메시지에 남은 예산을 결정적으로 배분한다. 후보 개수/정렬과 제외 이유를 기록한다. 오래된 대화를 보관하면서 검색 가능하게 하고, 최근 N개만 남기고 원문을 삭제하지 않는다.

첫 버전 검색은 범위 필터와 정규화된 어휘 일치로 시작한다. 한국어 입력·동명 에이전트·다른 프로젝트를 포함하는 회귀를 둔다. 검색 결과에는 원문 ID가 붙는다. 의미 검색 성능이 필요하다는 실제 평가가 나온 뒤 embedding을 추가한다. 검색이 없으면 `일치하는 이전 기록 없음`을 표시하며 기억한다고 추측하지 않는다.

자동 요약에는 기존 요약 버전과 이후의 **연속된 종료 turn 구간**을 명시적으로 제공한다. 현재 응답 중인 turn은 다음 호출부터 요약 대상이 된다. 한도 때문에 일부 구간만 들어가면 실제 전달한 연속 구간의 끝까지만 summaryThrough를 전진시킨다. 검색으로 선택한 흩어진 과거 메시지를 근거로 요약 범위를 건너뛰지 않는다. 요약이 뒤처져도 원문과 최근 대화는 유지하고 요약 경계를 표시한다.

모델은 자동 요약의 요약문·결정·미해결 질문과 출처 ID만 반환한다. 서버가 해당 요약 구간/직전 유효 요약에 없는 출처를 거절하고 요약 길이/구조를 검증한다. 답변은 유효하지만 요약이 무효이면 답변을 저장하고 기존 요약/경계를 보존하며 `요약 갱신 실패`를 표시한다. 요약의 사실성까지 보장한다고 주장하지 않는다. 사용자는 요약을 보거나 초기화할 수 있고, 원문은 남는다. 장기 기억 자동 승인과 검증 성공 자동 학습은 하지 않는다.

대화마다 `참조한 기억 N개 / 최근 대화 N개 / 이전 검색 N개 / 선택 실행`을 펼쳐볼 수 있다. 표시한 목록과 실제 provider payload의 ID/hash를 일치시킨다. 숨겨진 추론은 저장/표시하지 않는다.

요약 초기화는 summary revision을 증가시킨다. 진행 중 응답의 요약 저장은 expected summary revision이 일치할 때만 허용하여 사용자가 초기화한 옛 요약이 되살아나지 않게 한다. 답변 저장과 요약 저장 성공 여부는 분리한다.

## 4. 저장과 트랜잭션

대화는 snapshot polling에 전체 transcript를 싣지 않는다. 별도 PostgreSQL 테이블을 두고 thread 목록/요약과 페이지 단위 메시지만 조회한다. 모든 key/쿼리는 workspace를 포함하며 프로젝트/agent/feature 관계를 서버에서 검증한다. renderer 필터로 격리를 대신하지 않는다. 기존 local-owner 인증 모델을 넘는 다중 사용자 보안/회사 SSO를 주장하지 않는다.

- Thread: ID, workspace, project, agent, optional feature, revision/epoch, created/updated, summary와 summaryThrough, archived 상태.
- Turn: request ID, thread, ordinal, 사용자 입력, assistant 응답/구조화 요약, 상태 `pending/completed/failed/interrupted/cancelled`, 입력 digest, context manifest, 연결 ID/version·모델, usage가 있으면 token 수, 안전한 오류 메시지.
- Memory: ID, project, agent, optional feature, title/body, revision, source refs, created/updated, active/archived, author. 작은 큐레이션 집합은 Workspace의 프로젝트 데이터에 두어 승인 바인딩과 같은 트랜잭션으로 관리한다.

새 thread/turn 요청은 idempotency key와 payload digest로 중복 전송을 막는다. 이미 처리한 요청 ID의 다른 payload는 거절한다. 한 thread에 동시 모델 요청은 하나, 앱 전체 상담 요청은 최대 2개다. runner 슬롯과 상담 요청 수를 섞지 않는다. 네트워크 호출 동안 DB 행 잠금을 유지하지 않는다.

모델 응답 저장 전 thread epoch·pending turn·연결 version을 다시 검사한다. thread 삭제/취소/연결 변경 뒤 도착한 응답을 되살리지 않는다. 앱 종료 시 요청을 취소하며 재시작하면 남은 pending을 interrupted로 표시한다. 강제 종료/DB 실패 뒤 자동으로 유료 요청을 재전송하지 않고 `답변 재요청`을 사용자가 선택한다.

동일 요청 ID 재전송은 조회/중복 방지이며 신규 provider 호출이 아니다. 사용자가 선택한 재요청은 새 ID와 retryOf로 원래 실패/중단 turn을 연결한다. 요청은 시작 시 Store 인스턴스·workspace key를 고정하고 전역 store 변수가 바뀌었다고 새 DB에 응답을 쓰지 않는다. 처음에는 thread당 본문 5MiB·workspace 대화 총량 100MiB 상한을 두어 초과 요청을 원문 손실 없이 거절하고 대화 정리 경로를 안내한다. 자동 원문 삭제는 하지 않는다.

저장량 검사에는 사용자 입력뿐 아니라 허용된 최대 응답·요약·manifest 크기의 예약분도 포함한다. 요청 전 예약과 종료 후 실측 반영을 트랜잭션으로 처리해 동시 상담 두 개가 한도를 넘기지 못하게 한다. 용량 부족이면 provider 호출 전에 거절한다.

대화 삭제·파생 기억 중지는 **workspace → thread** 순서의 한 트랜잭션으로 처리한다. 실행 중 변경 금지 조건을 먼저 검사하고 실패하면 원문도 삭제하지 않는다. 삭제된 thread epoch/tombstone은 같은 ID의 늦은 응답/중복 요청을 거절하며 내용은 포함하지 않는다. 모든 대화/기억 변경에서 이 잠금 순서를 일관되게 유지한다.

DB 이전/백업에 대화 테이블도 포함하고 원본/대상 hash 검증을 확장한다. 이전 시작 전에 새 상담을 차단하고 진행 중 상담이 종료되거나 취소 상태로 저장된 것을 확인한다. pending 상담이 남거나 종료 상태 저장이 실패하면 이전을 거절하고 기존 환경을 유지한다. 기존 사용자의 데이터에 additive migration만 적용하며, 대화/기억이 있는 대상 DB를 빈 DB로 오판하지 않는다. 이전 실패 시 기존 환경을 유지한다. harness import/export에는 사적 대화와 기억을 자동 포함하지 않는다.

## 5. 실제 실행으로 기억 전달

장기 기억의 변경은 기존 프로젝트 지침 변경과 같은 승인 영향으로 취급한다. 최초 구현에서는 영향 계산의 복잡성을 줄여 **해당 프로젝트의 설계 승인을 재확인하는 정책**을 쓴다. 다른 프로젝트의 승인은 유지한다. 저장 전에 영향 안내를 표시한다.

해당 프로젝트에 queued/active 또는 종료 미확인 run이 있으면 장기 작업 기억 변경을 막는다. 대화와 자동 상담 요약은 계속 사용할 수 있다. 먼저 기존 작업을 정상 종료한 뒤 기억을 변경하게 한다. 실행 중인 입력이 조용히 바뀌지 않는다.

policyBinding/approvalBinding에 활성 장기 기억의 안정된 내용과 revision을 포함한다. run 요청 때 적용 기억을 resolved harness에 스냅샷하고 각 에이전트에 자기 범위의 기억만 전달한다. 사용한 memory ID/revision/hash를 실행 근거에 남긴다. runner는 현재 DB에서 기억을 다시 검색해 기존 실행 입력을 덮어쓰지 않는다. 재시도도 기존 approval/binding 검사를 통과해야 한다.

binding의 기억 항목은 active ID 순으로 정렬한 ID·revision·project/agent/feature 범위·title/body·출처 식별자를 canonical 직렬화한다. 조회 시각 등 변하는 메타데이터를 포함하지 않는다. 빈 기존 데이터는 기존 승인 hash를 불필요하게 바꾸지 않는 호환 표현으로 처리한다. 기억 변경 명령은 expected revision을 검증하고 project 전체 기존 승인 무효화/재게시 규칙을 같은 트랜잭션에서 적용한다.

기억은 별도 `참고 기록 — 명령·승인·검증 근거 아님` 구역에 넣는다. 모델 지시만으로 prompt injection을 완벽히 해결한다고 주장하지 않는다. 실제 도구 권한·승인·고정 검사·읽기 전용 리뷰 경계를 프로그램이 유지한다. 에이전트의 최종 결과가 자동으로 장기 작업 기억이 되지는 않는다.

실행 체크포인트는 기존 소스 tree와 실행 결과를 사용한다. 이번에 CLI 세션 persistence/resume를 켜거나 병렬 에이전트가 같은 home/memory 디렉토리를 공유하게 하지 않는다.

## 6. 연결·응답·비용·개인정보

현재 vault가 지원하는 Anthropic Messages 호환 endpoint와 agent/project의 검증된 연결을 사용한다. 새로운 OpenAI provider/SDK를 연결했다고 주장하지 않는다. 같은 설정의 모델을 쓴 상담이 실행 중인 CLI 세션과 동일하다고 표현하지 않는다. API key는 main/vault에만 남고 renderer·대화·기억·export에 넣지 않는다.

모델은 도구 없이 응답과 요약만 생성한다. HTTPS endpoint 검사·redirect 거부·본문 크기 제한·60초 timeout·불완전 응답 검증·안전한 오류 메시지를 적용한다. 응답 HTML은 실행하지 않는다. 사용자/로그/문서/기억은 낮은 신뢰의 자료로 구분한다.

보수적인 입력 크기 예산과 답변 출력 상한을 둔다. 최초 값: 상담 입력 총량 64KiB, 한 사용자 메시지 8,000자, 답변+구조화 요약 출력 최대 4,096 tokens, 자동 요약 최대 4,000자, 장기 기억 1건 최대 2,000자/에이전트당 활성 20건·총 12,000자. 필수 harness와 현재 질문이 입력 한도를 넘으면 조용히 자르지 않고 원인과 조정 경로를 표시한다. 상담에는 기억 최대 8건/8,000자, 최근 대화 최대 12건/16,000자, 이전 검색 최대 4건을 우선 한도로 하되 전체 byte 예산이 우선한다. runner에는 해당 범위의 활성 작업 기억을 모두 고정하되 최대 총량을 저장 시 강제한다. 후보 기억/원문은 유한 개수만 선택하고 생략 사실을 표시한다. 문자/바이트 한도를 정확한 모델 token 수라고 표시하지 않는다.

token usage가 실제 응답에 있으면 그대로 보관한다. 모델별 가격표 없이 달러 비용을 계산하거나 미보고를 0으로 표시하지 않는다. 자동 background 요약 호출을 추가하지 않고 사용자 답변 호출에서 구조화 요약을 함께 받는다. 요청 실패 시 중복 과금 가능성을 알리고 자동 재시도하지 않는다.

대화·기억은 현재 로컬 PostgreSQL 저장 방식을 따른다. 대화 본문까지 암호화된 저장소라고 주장하지 않는다. 설정된 외부 endpoint에 전송되는 내용과 범위를 UI에서 확인 가능하게 한다. 알려진 키와 인증 헤더 등 비밀이 오류·로그에 유출되지 않게 차단/마스킹하며 모든 임의 비밀을 완벽히 탐지한다고 보장하지 않는다.

기억의 `사용 중지`는 미래 검색/실행 입력에서 제외하며 기존 실행 근거는 보존한다. `대화 삭제`는 원문·요약을 삭제하고 파생 기억의 처리 범위를 확인한다. 파생 기억을 함께 중지하는 경우 같은 프로젝트의 실행/승인 영향 규칙을 적용한다. 진행 중 응답은 취소하고 늦게 도착한 응답을 버린다. 기존 실행 입력·별도 backup·외부 provider에 이미 전달된 사본까지 지웠다고 표시하지 않는다. 이 한계를 삭제 확인에 구체적으로 안내한다.

## 8. 배포 품질과 Mac App Store

이번 목표는 실제 사용할 수 있는 기능·복구·데이터 유지·UI 품질이다. 현재 Docker/로컬 프로세스 실행 구조로 Mac App Store 제출 가능하다고 보증하지 않는다. Apple은 Mac App Store 앱의 App Sandbox, self-contained 설치와 추가 코드 설치 등에 요건을 둔다. 현재 구조와의 적합성은 별도 배포 설계·실기 검토가 필요하다.

이번 기능 때문에 실행기를 임의로 원격 서비스로 전환하거나 사용자 Docker/데이터를 제거하지 않는다. Developer ID 서명/공증, MAS entitlement와 배포 구조, 개인정보 문서/지원 경로, 다른 Mac에서의 설치 및 실제 provider 검증을 별도 release gate로 보고한다. `check:mac` 통과를 앱스토어 심사 통과라고 부르지 않는다.
