# 전역 관제 세부 설계 독립 리뷰

검토일: 2026-09-28 · 검토: Astra 독립 설계 리뷰 담당

**결론: 설계 정합성 독립 리뷰 통과. 사용자 본인의 설계 승인은 대기 중이다.** 이 결과는 구현 승인, 제품 동작 검증, PR 승인 또는 사용자 승인을 대신하지 않는다.

## 고정한 검토 대상

- 설계: [PORTFOLIO-CONTROL-CENTER.md](PORTFOLIO-CONTROL-CENTER.md)
- 설계 SHA256: `00c82cc00b333ead296f91a1324cf466d31e54f4ff1bac4052bec08ec844e5da`
- 대조한 제품 HEAD: `b7c33cebee9630848293c77bc0470a03a2544e23`
- 범위: 프로젝트×단계 관제, 판단할 일, 역할별 실제 실행 맵, 공통 Inspector와 기존 상세 탐색. Snapshot의 읽기 projection이며 새 runner, 예산 enforcement, 전역 비서, 팀 서버는 제외한다.

설계 작성 에이전트와 분리된 문맥에서 AGENTS.md, 공유 contracts/runtime/harness/execution-graph, runner의 점유·heartbeat·재시도, App의 snapshot 채택·탐색, navigation/useNavigationHistory/presentation, RunPanel의 run 선택 및 기존 웹 회귀 접점을 직접 읽었다. 위 해시 이후 설계 의미가 달라지면 변경 부분을 다시 리뷰해야 한다.

## 발견 및 수정 확인

| ID  | 초안의 위험                                                                                                                                                     | 최종 설계에서 확인한 해결                                                                                                                                                                          |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | 부모가 active이고 heartbeat가 최신이어도 취소 요청 중인 agent를 정상 작업 중으로 셀 수 있었다.                                                                  | §3.2–3.3은 cancelRequested를 활성 agent에서 제외하고 중단 요청 표시와 종료까지 슬롯 유지를 명시한다. AC-02에 nonterminal 취소 사례를 추가했다.                                                     |
| R2  | 기존 App.refresh는 낮은 revision 응답을 버려도 lastSync를 갱신한다. 이를 재사용하면 오래된 snapshot의 최신성을 잘못 회복한다.                                   | §3.4는 채택된 snapshot 조회 시각을 사용한다. 낮은 revision은 화면/시각 모두 거부하고 동일 revision 정상 조회는 시각 갱신을 허용한다. AC-06은 역순 응답과 끝나지 않는 조회의 stale 전환을 포함한다. |
| R3  | RunPanel의 선택 run은 localStorage를 mount 시 useState 초기값으로 읽는다. 같은 기능의 다른 run으로 돌아올 때 저장값만 바꾸면 child는 이전 run을 유지할 수 있다. | AC-08에 동일 feature의 다른 과거 run 재진입 시 실제 child 선택까지 갱신하는 조건을 명시했다.                                                                                                       |

R1/R2는 운영 상태를 오인하게 만들 수 있는 설계 결함으로 수정 요청했고, R3는 정확한 탐색 계약을 검사 가능하게 구체화했다. 최종본에 미해결 차단 지적은 없다.

## 안전성과 실행 가능성 판단

| 검토 축            | 판단 및 구현 시 지켜야 할 경계                                                                                                                                                                                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 실행/점유          | queued, non-queued active, 슬롯 점유, 실제 agent 수를 분리한다. 과거 run의 종료 미확인도 모든 run 집계에 남긴다. runner 메모리 active Map을 Snapshot이 담지 못하므로 실행 가능/큐 순서 보증을 하지 않는다.    |
| 실행 정체성과 근거 | runId+attempt+executionId를 key로 쓰고 현재 시도와 과거 선택을 분리한다. 현재 정의 revision으로 과거 실행을 덮지 않으며 계획 completed를 제품 완료로 표시하지 않는다.                                         |
| 최신성             | 채택 snapshot 시각, runner heartbeat, 활동 event를 별도로 다룬다. 5초/30초 기준은 표시 신뢰도 규칙이며 취소/재시작 정책이 아니다. UI 시계는 조회 완료 여부와 독립적으로 움직인다.                             |
| 비용               | 모든 runtime run을 run당 한 번 합산하며 costReported가 없는 값을 0으로 만들지 않는다. 보고된 값도 일부일 수 있음을 밝히고 agent/attempt 비용, 청구액, 예산 잔액을 만들어내지 않는다.                          |
| 행동 및 권한       | 관제는 조회/선택/기존 상세 이동만 한다. 판단 목록은 현재 근거에서 생성하며 승인·재시도·취소·병합을 자동 실행하지 않는다. 사용자 설계 승인은 기존 본인 인증 경로에 남는다.                                     |
| 탐색               | 관제 selection과 기능 상세 selected를 분리한다. 정확한 feature/run/attempt와 목적 탭을 전달하며 뒤로/앞으로, 설정 child 대상, 과거 run 재진입을 회귀 검사한다.                                                |
| 접근성             | 1024px에서 Inspector를 아래로 옮기고 페이지 가로 넘침을 막는다. 키보드 선택·진입·복귀, 포커스 유지, 문구 기반 상태, polling 중 순서/공지 안정성을 요구한다.                                                   |
| 검증               | AC-01–12가 상태/비용/권한/UX/native 경계를 다룬다. 순수 projection과 웹 회귀 외 실제 Electron snapshot·실패 복구·재진입 증거를 별도로 요구하므로 기존 desktop suite 결과만으로 새 기능 완료를 주장할 수 없다. |

renderer의 데이터 채택 시각과 상세 진입 문맥 보완은 이번 UI 범위에 필요한 변경이다. 기존 executionGraph/workState를 그대로 전역 집계로 사용하면 queued·freshness 조건이 부족하므로 설계에 명시한 순수 projection에서 조건을 적용해야 한다. 서버/DB/runner 명령 변경 없이 구현 가능한 계약이다.

## 수행한 검사와 남은 일

수행한 검사는 소스와 설계의 정적 대조, 수정된 R1–R3 재확인, 대상 HEAD 및 설계 SHA256 확인이다. 제품 코드·테스트는 변경하지 않았고 앱 실행, 단위/웹/native 테스트, 모델 호출, OS 인증, commit/push/PR은 수행하지 않았다. 따라서 제품 구현의 AC 통과를 기록하지 않는다.

다음 단계는 사용자 본인의 이 고정 설계 승인이다. 그 원문·범위·날짜를 기록한 뒤 Terra가 구현하고 Astra가 정확한 구현 head/base를 독립 리뷰한다. PR 머지는 최신 사용자 위임과 저장소 절차를 따르며, 이 설계 리뷰가 사용자 설계 승인이나 구현 검증으로 재사용되어서는 안 된다.
