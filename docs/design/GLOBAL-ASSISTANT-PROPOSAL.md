# 루프리 전역 비서와 대화형 에이전트 구성 · 설계 제안

상태: 사용자 검토용. 신규 기능의 구현·테스트·머지를 완료한 문서가 아니다. 기존 v0.3의 단계별 복수 에이전트와 Markdown 관리 위에 추가한다. 이번 사용자 요청은 모든 프로젝트를 관리하는 비서와 대화로 지침을 만들어 에이전트를 생성하는 경험이다.

## 요구사항과 현재 구분

- 확정된 사용자 요구: 모든 등록 프로젝트의 현황을 한곳에서 파악하는 전역 비서, 단계별 여러 에이전트, Markdown 직접 입력과 대화를 통한 지침 작성.
- 이미 구현: 전역/프로젝트 범위 에이전트 생성·편집·복제·보관, Markdown 가져오기/내보내기, 단계별 순서·필수 여부·모델 연결, 실행 시 버전·지침 스냅샷.
- 신규 제안: 전역 비서 채팅, 근거 있는 전체 현황 요약, 조치 제안 카드, 대화형 에이전트/워크플로우 초안과 적용, 비서 자체의 지침·연결 설정.
- 전역은 현재 Mac의 루프리 워크스페이스다. 다른 개발자의 Mac이나 미등록 GitHub 저장소까지 자동 조회하는 뜻이 아니다.

## 역할 구조

사용자 ↔ 전역 비서 ↔ 루프리의 조회·제안·적용 도구 ↔ 프로젝트별 단계 실행기.

전역 비서는 현황 파악·원인 설명·다음 행동 제안·구성 작성을 담당한다. 단계 에이전트는 각 기능의 요구사항·설계·구현·검증·리뷰를 수행한다. 상태 전이·권한·승인·필수 검사·동시 실행 한도는 기존 프로그램이 소유한다. 첫 범위에서 비서에 임의 shell/SQL/코드 쓰기 권한을 주지 않는다.

비서 자체의 Markdown은 요약 방식, 우선순위 판단, 보고 언어 등 운영 지침이다. 모든 단계에 적용되는 전역 개발 지침과 별도로 저장한다. 비서 지침 수정만으로 프로젝트 개발 계약이 변경되지는 않는다.

## 대표 사용자 흐름

### 전체 현황

“지금 진행 중인 것과 내가 해야 할 것 알려줘” → 프로젝트·기능·실행 상태를 조회 → 확인 시각과 근거 링크가 있는 상태 카드 생성 → 승인 대기·필수 검사 실패·완료 후보 우선 표시.

예시 상태 문구는 설계 예시이며 샘플 완료 기록을 제품 DB에 생성하지 않는다. 진행률·완료 예정 시간을 근거 없이 추정하지 않는다. 상태가 바뀌면 카드에 오래된 정보임을 표시하고 다시 조회한다. 기본 대시보드 집계는 로컬 코드가 수행하며, AI 요약은 대화 요청 시 호출한다. 지속 감시·정기 유료 호출은 별도 설정 범위다. 앱 종료/잠자기 중 동작을 보장하지 않는다.

### 대화로 에이전트 생성

“결제 프로젝트에 컨벤션 검증자와 보안 리뷰어를 만들어줘” → 관련 전역/프로젝트 지침 조회 → 두 에이전트의 Markdown 초안과 배치 제안 → 검토 카드 → 적용 → 실제 라이브러리/프로젝트 흐름에 저장.

카드는 이름·목적·공유 범위·단계·읽기/구현 권한·필수 여부·모델 연결·Markdown·영향받는 프로젝트/승인을 표시한다. Markdown은 바로 편집·복사·내보낼 수 있다. 같은 정의를 여러 프로젝트가 참조할 수 있고 프로젝트 전용으로 복제할 수 있다. 프로젝트 범위로 새로 생성하는 것을 기본값으로 한다.

직접 입력과 대화 생성은 같은 에이전트 스키마·검증·버전·저장 API를 사용한다. 생성된 Markdown만 채팅에 남기고 실제 등록했다고 주장하지 않는다. 적용 성공 후 실제 ID/revision과 배치 결과를 반환한다.

### 진행 조치

읽기·요약과 초안 작성은 대화 안에서 수행한다. 초기 버전의 비서는 조치 카드로 기존 기능/실행/설계 화면을 연다. 설계 승인, 실행 시작/재시도/중단, PR·머지는 해당 기존 절차에서 수행한다. 비서가 사용자 대신 본인 설계 승인하거나 실패를 통과로 변경하지 않는다. 별도 자동 시작/중단 권한은 후속 설계다.

## UI

- 사이드바의 고정 “비서” 진입점: 전체 현황, 내 조치 대기, 대화 기록.
- 프로젝트/기능 화면의 비서 패널: 현재 선택한 범위를 명시. 전역 조회가 필요할 때 범위를 눈에 보이게 확장.
- 대화 옆 제안 카드: 에이전트 지침과 워크플로우 변경 전후를 확인하고 수정/적용/폐기.
- 에이전트 화면: “직접 만들기 / Markdown 가져오기 / 비서와 만들기”. 비서의 대화 초안도 같은 편집기로 연결.
- 프로젝트별 표준 단계는 유지하며 단계 내부에 여러 역할을 배치. 임의 단계나 임의 DAG 편집은 이번 범위가 아니다.

## 기본 에이전트 제공 · 사용자 추가 요구

프로젝트를 만들면 기본 에이전트와 배치를 바로 사용할 수 있어야 한다. 빈 라이브러리에서 직접 모든 역할을 구성하도록 요구하지 않는다. 기존 프로젝트에는 변경 비교와 적용을 제공하며 기존 구성을 자동 덮어쓰지 않는다.

| 단계     | 기본 역할       | 기준                                       |
| -------- | --------------- | ------------------------------------------ |
| 요구사항 | 요구사항 정리자 | 목표·범위·AC와 미정 질문                   |
| 설계     | 설계자          | 구조·데이터·예외·검증·복구 계획            |
| 설계     | 설계 검토자     | 앞선 설계의 누락·영향·불필요한 복잡성 검토 |
| 구현     | 개발자          | 승인된 범위 구현과 테스트 변경안           |
| 검증     | 요구사항 검증자 | AC별 실제 근거 확인                        |
| 검증     | 컨벤션 검증자   | 전역/프로젝트 규칙과 고정 검사 확인        |
| 리뷰     | 코드 리뷰어     | 결함·회귀·유지보수 검토                    |

각 정의에는 기본 Markdown을 제공하고 수정·복제·추가·모델 변경을 허용한다. 템플릿 ID/version과 사용자 수정 여부를 별도 보관하고 템플릿 업데이트는 비교 후 적용한다. 기본 정의와 배치는 프로젝트 생성과 함께 원자적으로 저장한다. 설계 검토자의 결과는 사람의 승인 근거로 보여주며 승인 자체를 대체하지 않는다. 기존 필수 테스트/설정 보호 규칙을 일반 개발자가 해제하지 않는다. 테스트 생성·변경안을 자동으로 승인하는 확장은 별도 계약이 필요하다.

## 프로젝트 흐름 시각화 · 사용자 추가 요구

핵심 질문은 “어떤 프로젝트의 어떤 기능이 어디까지 왔고, 무엇 때문에 기다리며, 내가 지금 무엇을 해야 하는가”다. 전역 비서 대화와 별개로 화면 자체에서 답을 읽을 수 있어야 한다. 현재 실행 이력 목록은 기반으로 유지하되 다음 화면을 추가한다. 아래 내용은 설계이며 현재 구현됐다는 뜻이 아니다.

### 세 단계 탐색

1. 전체 프로젝트: 프로젝트별 기능 수와 단계 분포, 실행 중 기능, 승인 대기·실패·현재 결과 확인 수, 마지막 동기화 시각. 승인 대기와 실패를 바로 필터링한다.
2. 프로젝트 상세: 기능을 행, 요구사항→설계→본인 승인→구현→고정 검사→리뷰→결과 확인을 열로 둔 흐름 표. 여러 기능을 한 화면에서 비교한다. 선택한 기능과 필터·스크롤은 갱신/화면 이동 후 유지한다.
3. 기능 상세: 선택 단계의 현재 에이전트·입력/출력 문서·최신 시도 검사·지적·변경 diff를 옆 패널에서 펼친다. 재시도·이전 설계 버전은 이력으로 분리한다. 원래 프로젝트 표의 문맥을 잃지 않는다.

설계 예시(제품에 넣을 샘플 작업이 아님):

```text
결제 프로젝트    실행 1 · 본인 승인 대기 1 · 확인 필요 1
기능             요구사항  설계   승인    구현   검사    리뷰   결과
간편결제 추가       완료    완료   대기     —      —       —      —
환불 안내 개선      완료    완료   완료    완료   실행 중   —      —
쿠폰 중복 적용      완료    완료   완료    수정 중 실패     —      —

선택: 환불 안내 개선 / 고정 검사
현재: Playwright 결제 실패 시나리오 실행 중
이번 시도: 필수 검사 2/3 통과 · 마지막 활동 10초 전
[검사 결과] [산출물] [비서에게 원인/상황 묻기]
```

### 표시 계약

- 완료/진행 중/대기/실패/중단/재검증 필요를 아이콘·텍스트·색으로 함께 표시한다. 색만으로 구분하지 않는다.
- 대기는 “본인 승인”, “같은 프로젝트 실행 중”, “전체 실행 슬롯 부족”, “선행 기능 미완료” 등 실제 이유를 보여준다. 아직 실행하지 않은 단계는 별도로 표시한다.
- 실패한 검사 다음 수정 시도는 구현 단계로 돌아온 것으로 표시하고 “자동 수정 2번째 시도”를 붙인다. 앞선 실패와 현재 실행을 동시에 설명하되 이전 실패를 현재 상태로 합산하지 않는다.
- 프로젝트 집계는 기능별 최신 설계·유효 승인·현재 실행으로 계산한다. 모든 과거 run이나 모든 시도의 검사 통과 개수를 합산해 진행률로 쓰지 않는다.
- 고정 검사는 이번 코드/시도의 필수 검사 통과 수, 에이전트는 이번 시도의 필수 에이전트 완료 수를 표시한다. 기능 전체가 80% 완료됐다는 식의 추정 퍼센트나 임의 ETA를 만들지 않는다.
- 코드/지침/설계 변경으로 이전 근거가 무효화되면 이력은 보존하고 현재 단계는 재승인/재검증 필요로 바꾼다.
- ready_for_merge는 “검사·리뷰 통과 / 결과 확인”이다. GitHub 머지·배포 사실을 확인하기 전에는 머지 완료/배포 완료로 표시하지 않는다.
- 동기화 실패 시 마지막 snapshot을 유지하면서 “마지막 확인 시각 / 연결 끊김”을 표시한다. 상태 불명과 실제 작업 실패를 구분한다.
- 설계 승인 화면은 채팅 요약 대신 설계 원문·변경점·검토 항목·차단 의견을 바로 보여준다. 승인 대기 행의 “설계 검토”가 이 화면으로 연결된다.
- 전역 비서도 화면과 같은 상태 집계/근거를 조회한다. 모델이 상태나 완료 수를 별도로 만들어 기록하지 않는다.

### 화면 방향과 접근성

기존 Electron 앱의 사이드바·테마를 유지한다. 주 화면은 넓은 흐름 표, 오른쪽은 선택한 기능 상세/비서 패널이며 모든 본문을 왼쪽 정렬한다. 큰 숫자 카드보다 기능 흐름과 조치 이유에 공간을 배분한다. 기본 서체는 기존 시스템 한글 서체를 사용하고, 이름·현재 단계·막힌 이유 순서로 강조한다.

색은 기존 테마 토큰을 우선 재사용한다. 방향값은 밝은 배경 #F6F7F9, 어두운 배경 #20242B, 실행 강조 #2C5DC1, 완료 #237A53, 대기 #986416, 실패 #B93838이며 실제 구현에서 테마별 대비를 검증한다. 승인 대기와 오류는 서로 다른 아이콘/문구를 사용한다. 장식 애니메이션 대신 실제 갱신된 행만 잠깐 강조하며 reduced motion을 존중한다.

1024×700에서는 상세를 전용 화면/접이식 패널로 전환하고 흐름 표 첫 열을 고정한다. 키보드로 행/단계 선택과 상세 열기·닫기를 수행할 수 있어야 한다. 전체 빈 상태는 프로젝트 등록, 프로젝트 빈 상태는 첫 요구사항 작성을 안내한다.

### 추가 인수 기준

- 두 프로젝트의 여러 기능이 설계 승인 대기/검사 진행/실패 후 수정/결과 확인 상태일 때 화면과 비서의 집계가 일치한다.
- 재시도 이력과 오래된 성공 기록이 현재 기능 수·검사 통과 수를 부풀리지 않는다.
- 설계 변경·승인 철회·필수 검사 실패·취소·연결 끊김이 서로 다른 상태와 다음 행동으로 표시된다.
- 상태 갱신이 사용자의 선택·작성 중 입력·스크롤을 덮어쓰지 않는다.
- 기본 에이전트와 흐름이 신규 프로젝트 생성 시 제공되고, 템플릿 업데이트가 사용자 수정 지침을 덮어쓰지 않는다.
- 라이트/다크·작은 창·키보드에서 설계 검토와 실패 근거 접근을 확인한다.

## 데이터와 적용 계약

- AssistantProfile: Markdown 지침 revision, 선택한 연결 ID/version. key는 기존 vault에서만 관리.
- Conversation/Message: 워크스페이스 및 선택 프로젝트, 사용자/비서 메시지, 사용한 도구와 근거 참조, 비용/실패 상태. 로컬 PostgreSQL 저장.
- Proposal: draft/applied/discarded/stale, 생성/수정할 agent·workflow 정의, 대상 ID와 expected revision, 영향 목록, 요청 ID, 적용 결과.
- Read tools: 전체 현황, 프로젝트 상세, 기능 설계/실행 근거, 적용 지침/에이전트 정의 조회. 필요한 범위만 모델에 제공하고 원문 key/DB 비밀번호는 제공하지 않는다.
- Apply tool: 검증된 구조의 에이전트/배치 변경만 한 트랜잭션으로 적용. 중복 요청은 같은 결과를 반환하고 일부만 생성되는 상태를 막는다.
- 기존 에이전트나 흐름 변경은 기존 승인 무효화·실행 중단 규칙을 그대로 따른다. 적용 직전 revision 재확인으로 오래된 제안을 거절하고 영향 카드 재생성을 안내한다.
- 저장소/에이전트 Markdown/로그는 참조 데이터이며 비서의 도구 권한을 확장하는 명령으로 취급하지 않는다. 비서의 모델 응답도 도메인 검증을 통과해야 저장한다.

## 인수 기준

1. 서로 다른 두 프로젝트의 실제 진행·실패·승인 대기를 구분하고 각 요약에 근거 화면과 확인 시각을 표시한다.
2. 대화로 만든 두 에이전트를 미리보기/수정 후 하나의 프로젝트에 적용하면 각각 올바른 단계·필수 여부·지침·모델로 저장된다.
3. Markdown 직접 입력과 대화 생성의 결과가 동일한 저장/실행 계약을 사용하며 재시작 후 유지된다.
4. 잘못된 모델 출력·비용 한도·취소·저장 실패를 성공으로 표시하지 않고 기존 설정을 보존한다.
5. 같은 적용 요청을 반복해도 에이전트/배치가 중복되지 않고, 한 정의라도 유효하지 않으면 전체 적용이 취소된다.
6. 제안 뒤 프로젝트/지침이 변경되면 stale 처리하고 이전 상태로 덮어쓰지 않는다.
7. 변경으로 무효화되는 승인과 중단되는 실행을 적용 전에 표시한다. 새 정의만 생성하면 무관한 프로젝트의 승인은 유지한다.
8. 비서의 요청이나 Markdown으로 본인 설계 승인·검사·PR 승인 경계를 우회할 수 없다.
9. 기본 테스트는 격리된 모델 fixture로 수행한다. 실제 연결 검증은 앱에 등록한 연결과 합의한 비용 범위에서 별도로 수행하고 결과를 구분한다.

## 구현 순서와 검토할 결정

전체 현황·근거 조회 → 비서 대화와 초안 → 구성 변경 미리보기/원자적 적용 → 저장·복구·실패 테스트 순서로 진행한다. 중앙 팀 서버, 임의 shell, 자동 PR/머지, 무인 정기 모델 호출은 이번 제안에 포함하지 않는다.

권장 결정: 전역 비서는 한 곳에서 현황과 구성 초안을 관리하고, 실제 개발은 기존 단계 실행기에 맡긴다. 에이전트/흐름 변경은 검토 카드에서 적용하며 사람의 설계 승인은 유지한다. 이 설계 검토 후 구현 범위를 확정한다.

## 회사·프로젝트별 표준 하네스 · 추가 방향

사용자는 개별 회사와 프로젝트에 맞게 개발 흐름을 표준화하는 틀을 원한다. 다음 내용은 후속 설계 방향이며 현재 회사/조직 기능이 구현됐다는 뜻이 아니다.

표준의 구성 단위는 Markdown뿐 아니라 단계/기본 역할, 필수 에이전트와 검사, 승인 조건, 실행 환경·한도, 산출물 형식이다. 회사 표준 → 프로젝트 보완 → 단계/역할 지침 → 기능의 승인된 설계로 적용 출처를 표시한다. 모델이 지침 의미 충돌을 완벽하게 해결한다고 가정하지 않는다. 강제할 수 있는 규칙은 구조화한 설정과 실행 검사로 관리한다.

회사 표준의 필수 규칙과 프로젝트에서 수정 가능한 기본값을 구분한다. 프로젝트는 회사가 허용한 범위에서 역할·검사를 추가하거나 기본값을 바꾸며 필수 승인/검사를 조용히 약화하지 못한다. 회사 A와 회사 B는 별도 워크스페이스/표준 범위로 격리하고, 비서의 전체 조회도 현재 회사 경계를 따른다. API key는 공유 템플릿에 넣지 않는다. 실제 조직 격리는 저장/조회/도구 권한에서 구현해야 하며 화면 필터만으로 보장하지 않는다.

표준 템플릿에는 ID/version, 지침, 기본 에이전트, 배치, 필수 검사·승인 규칙을 포함한다. 프로젝트 생성 시 템플릿 버전을 선택하고 실행마다 실제 적용 버전을 고정한다. 표준 업데이트는 변경 비교·영향 범위·재승인 여부를 확인한 뒤 적용하며 사용자 수정이나 진행 중 실행을 자동 덮어쓰지 않는다. 관리자는 최신 필수 버전을 정할 수 있으나 실제 관리자 인증/권한/중앙 적용은 팀 기능 범위에서 설계한다.

단계적으로 로컬 템플릿 가져오기·내보내기 → Git으로 회사 표준 버전 공유 → 중앙 인증·정책 배포·감사 및 CI/머지 검사로 확대할 수 있다. 로컬 앱과 Git 공유만으로 모든 개발자의 우회를 서버에서 막는다고 주장하지 않는다. 회사 전체의 필수 기준 강제가 필요하면 신뢰할 수 있는 CI·머지 권한 또는 팀 서버의 검증이 필요하다. 중앙 서비스 도입은 현재의 로컬 실행 구조를 없애는 결정과 별개다.

현재 구현은 단일 로컬 워크스페이스의 전역/프로젝트 지침과 단계별 에이전트다. 회사 템플릿·관리자 배포·다중 회사 격리·중앙 강제는 미구현이며 이번 전역 비서 제안에 이미 완성된 기능처럼 포함하지 않는다. 목표는 같은 승인·최소 품질 기준과 근거를 적용하는 것이며 모든 모델 결과가 동일한 품질임을 보장하는 것은 아니다.

설정 파일 구조·Git 버전 고정·import/export·프로젝트/기능 경로 범위는 [하네스 패키지 검토안](HARNESS-PACKAGE-PROPOSAL.md)에서 구체화했다. UI와 비서가 같은 portable 설정 모델을 사용하며 구현 전에 두 제안을 함께 검토한다.
