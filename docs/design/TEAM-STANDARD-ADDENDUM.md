# 루프리의 제품 목표 — 팀 개발 방식과 품질의 표준화

2026-09-18 · 사용자 목적 구체화 반영 · **설계 검토 대기, 구현 승인 아님**

[v0.2 설계](PRODUCT-DESIGN-v0.2.md)의 보충 문서다. 이미 앱에 게시한 v0.2 원문과 hash는 유지한다. 다음 구현 검토에는 이 보충 문서도 함께 포함한다.

## 제품이 달성할 결과

**누가 개발하든 팀이 정한 좋은 개발 절차를 기본으로 따르고, 동일한 품질 기준에 따라 검증된 결과를 내도록 한다.** 에이전트 실행, 병렬 처리, 상태 화면은 이를 위한 기능이다.

품질의 편차를 줄이는 데서 끝내지 않고, 실제 결함과 재작업을 분석해 표준을 계속 개선한다. ‘최상의 퀄리티’는 기능 정확성·설계 적합성·유지보수성·사용성·보안·운영 안정성으로 구체화한다. 비용과 속도는 이 기준을 충족한 결과 사이에서 비교한다.

## 모든 개발자가 따를 기본 흐름

| 단계      | 반드시 만드는 결과                                                 | 다음 단계로 넘어가는 조건                             |
| --------- | ------------------------------------------------------------------ | ----------------------------------------------------- |
| 요구사항  | 해결할 문제, 대상 사용자, 범위/제외 범위, 완료 기준, 예외 시나리오 | 결과를 검증할 수 있고 중요한 미정 사항이 정리됨       |
| 설계      | 사용자 흐름, 구조, API/데이터, 영향, 테스트 계획, 적용/복구 계획   | AI 사전 점검 후 사용자 본인이 해당 버전을 승인        |
| 구현      | 승인 범위의 변경, 작은 단위의 검사 결과, 결정/진행 기록            | 필수 정적 검사·단위/통합 검사와 변경 영향 확인        |
| 리뷰·검증 | 코드 리뷰 지적, 완료 기준별 증거, 필요한 실제 웹 시나리오          | 차단 문제 해결, 필수 검사 통과, 현재 코드와 증거 일치 |
| 전달      | 변경 요약, diff, 검증 결과, 알려진 제한, 적용/복구 방법            | 기존 저장소 병합·배포 정책 충족                       |
| 개선      | 발생한 결함·재작업의 원인과 표준 개선안                            | 기존 사례에 재검증한 뒤 팀 표준의 새 버전으로 게시    |

AI가 설계를 초안 작성하고 미흡한 내용을 먼저 보완해 사용자에게 제출한다. 사용자는 핵심 결정과 영향을 검토한다. 승인 후에는 범위 안의 구현·자동 리뷰·테스트·한도 내 수정에 매번 개입할 필요가 없다.

## 표준은 실행 가능한 계약으로 관리한다

팀 표준에는 단계별 입력·필수 산출물·검사·전이 조건·역할·실패 처리·완료 판정·버전을 함께 저장한다. 자연어 지침은 판단을 안내하고, 프로그램은 필수 조건을 강제한다. 프롬프트에 ‘잘 개발하라’고 적는 것만으로 완료하지 않는다.

개발자가 새 기능을 만들 때 승인된 표준이 자동 적용된다. 매번 프롬프트, 리뷰 순서, 테스트 도구를 직접 조립하지 않아도 된다. 실행 전과 결과 화면에서 적용한 표준 버전과 프로젝트 설정을 확인할 수 있다.

| 관리 단위       | 담을 내용                                           | 변경 원칙                                                     |
| --------------- | --------------------------------------------------- | ------------------------------------------------------------- |
| 팀 표준         | 공통 개발 단계, 필수 산출물·품질 관문, 승인 원칙    | 지정 관리자가 버전 게시; AI는 변경 제안만 가능                |
| 프로젝트 프로필 | 언어/구조, 빌드·검사 명령, 테스트 환경, 도메인 규칙 | 팀 기준 충족 여부 검사; 서로 다른 기술을 하나로 강제하지 않음 |
| 단계 지침       | 요구 정리·설계·구현·검증별 수행 방법                | 해당 단계에 필요한 문맥만 주입                                |
| 에이전트 역할   | 설계자·구현자·리뷰어의 도구/권한/검토 관점          | 역할 이름만 달리한 것이 아니라 권한과 결과 계약도 분리        |
| 기능 계약       | 이번 목표, 완료 기준, 승인 설계, 작업별 제한        | 상위 기준을 약화할 수 없음                                    |

표준 프로필은 신규 기능·버그 수정·유지보수를 구분한다. 공통 승인·검증 원칙은 같지만, 작은 수정에 불필요한 대규모 설계 산출물을 요구하지 않는다. 예를 들어 UI 변경에는 브라우저 흐름, API 변경에는 계약/권한 검사, 데이터 변경에는 마이그레이션·복구 검사를 필수로 추가한다. 사용하지 않는 검사는 명시적으로 비해당 처리하며, 에이전트가 임의로 생략하지 못한다.

## 품질이 사람의 숙련도에 덜 의존하도록 만드는 장치

1. **시작할 때 빠뜨리지 않기:** 요구사항·설계 템플릿과 누락 검사로 중요한 결정을 먼저 드러낸다.
2. **검증 가능한 설계 승인:** 어떤 결과를 어떤 방법으로 확인할지 사용자 승인 전에 정의한다.
3. **같은 환경에서 검증:** 도구·의존성·검사 명령을 실행 프로필에 고정해 개인 환경 차이를 줄인다.
4. **자기 선언으로 완료하지 않기:** 구현과 리뷰를 분리하고, 필수 검사와 AC 증거로 프로그램이 완료를 판정한다.
5. **실패를 자동으로 처리하기:** 승인 범위 안의 오류는 한도 내 수정·재검증하고, 요구/설계 변경만 다시 사용자에게 올린다.
6. **결함을 다음 표준에 반영하기:** 반복되는 문제를 회귀 시나리오·지침 개선으로 제안하고 효과를 확인한다.

모든 결과가 자동으로 최고 품질이 된다고 보장하는 대신, 미달한 결과가 통과하지 않게 하고 좋은 결과를 재현할 조건을 축적한다. AI 리뷰 점수 하나로 통과시키거나 결함을 발견한 테스트를 약화해서 통과시키지 않는다.

## 화면의 우선순위

- **팀 표준:** 현재 적용 버전, 단계별 결과물과 통과 조건, 프로젝트별 적용 상태.
- **설계 검토함:** 본인이 판단할 주요 결정, 변경 영향, 미해결 문제, 승인할 버전.
- **진행 상황:** 실제 단계, 다음 통과 조건, 막힌 원인, 완료 기준별 증거.
- **품질 현황:** 배포 후 결함·회귀, 설계 승인 이후 재작업, 첫 검증 통과, 사람 개입, 검증된 완료 건당 비용/시간.

개발자별 코드량이나 AI 점수 순위를 주된 지표로 삼지 않는다. 프로젝트·작업 유형·위험 수준·모델/표준 버전을 구분해 비교한다. 아직 사후 품질을 관찰하지 못한 작업은 ‘결함 없음’으로 간주하지 않는다.

## v0.2 구현 순서 보완

### 라이트·다크 모드

다크 모드는 기본 지원 요구사항이다. 현재 M1에는 라이트/다크 수동 전환과 선택 저장이 구현되어 있고, 시스템 설정 연동은 아직 없다. 다음 UI 보완은 `시스템 설정 따르기 / 라이트 / 다크`를 제공하고 최초 기본값은 시스템 설정으로 한다. 수동 선택은 재시작 후에도 유지하며 시스템 모드에서만 macOS 테마 변경을 따른다.

설계 문서·코드 diff·로그·입력 폼·팝업·승인/오류/비활성 상태까지 같은 테마 기준으로 검증한다. 상태는 색상만으로 구분하지 않고 텍스트·아이콘을 함께 사용한다. 두 테마에서 주요 작업 흐름, 키보드 포커스, 글자 대비, 최초 로딩 시 테마 깜빡임을 확인한다. 이 항목은 요구·검증 기준의 추가이며 이번에 테마 코드를 변경한 것은 아니다.

### 개발 순서

M2-A에 **버전이 있는 팀 표준과 프로젝트 실행 프로필**을 포함한다. 본인 승인·API 연결·저장소 등록이 이 표준에 묶여야 한다. 첫 구현은 코드로 정의한 고정 단계와 설정 폼으로 제공하고, 자유로운 드래그 방식의 워크플로우 편집기는 후순위로 둔다.

M2-B는 이 계약으로 실제 단일 실행을 완료하고, M2-C는 웹 검증·복구·병렬 작업에서도 같은 기준이 유지되는지 확인한다. M3에서는 실제 팀 구성원·권한·여러 기기에 적용한다. 병렬 실행 속도보다 한 작업의 품질 검증을 먼저 완성한다.

이 보완은 제품 목표와 설계의 정리다. 본인 설계 승인 전 구현하지 않는 원칙을 유지한다.
