# Git으로 공유하는 회사·프로젝트·기능 하네스

> 제안 당시 기록이다. 사용자가 후속으로 구현을 승인했으며 v0.4의 실제 계약/제한은 [Harness v1](../specs/HARNESS-V1.md)과 [승인 기록](V04-APPROVAL.md)을 따른다. 아래 YAML/부분 export/자동 동기화 등 전체 제안이 구현됐다는 뜻은 아니다.

검토일: 2026-09-18. 상태: 설계 제안, 미구현. 사용자는 Settings에서 프로젝트/기능 디렉토리·스텝·에이전트 하네스를 정리하고 import/export하여 팀 전용 Git 저장소로 통일하기를 요청했다. 앱 설치 ZIP 생성이나 새 GitHub 저장소 생성·게시 요청으로 해석하지 않는다.

## 판단

추천한다. 회사 표준 Git 저장소를 공유 설정의 원본으로 삼고, 프로젝트 저장소가 사용할 정확한 버전과 허용된 보완 설정을 관리하며, 루프리가 이를 해석·검증·시각화·실행하는 구조가 적합하다. UI와 대화는 같은 설정 모델을 편집하는 방법이다. DB의 실행 이력과 Git의 설정을 별도 책임으로 두어 두 개의 설정 원본이 생기지 않게 한다.

공유 설정에는 Markdown 지침과 구조화된 실행 계약이 함께 있어야 한다. Markdown만으로 승인·필수 검사·권한을 강제한다고 주장하지 않는다. 회사 표준 배포와 개발자가 우회할 수 없는 팀 차원의 강제는 별개다.

## 현재 구현과 차이

현재 에이전트 Markdown의 개별 가져오기/내보내기, 전역/프로젝트 지침, 단계별 배치, 실행 시 스냅샷은 구현돼 있다. 전체 하네스 패키지, Git 연결·동기화, 경로 범위, 회사 네임스페이스, portable ID 매핑, lockfile과 적용 비교는 신규다. 기존 내보내기는 연결·배치·회사 정책을 포함하지 않으므로 전체 하네스 백업이라고 표시하지 않는다.

## 세 가지 저장 범위

### 1. 회사 표준 저장소

```text
company-harness/
├── harness.yaml                   # 스키마·회사/패키지 ID·버전·지원 앱 버전
├── policies/
│   ├── development.md             # 공통 개발 지침
│   ├── security.md                # 공통 보안 지침
│   └── gates.yaml                 # 필수 검사·승인·변경 가능한 설정
├── agents/
│   ├── requirements.md
│   ├── designer.md
│   ├── design-reviewer.md
│   ├── developer.md
│   ├── acceptance-reviewer.md
│   ├── convention-reviewer.md
│   └── code-reviewer.md
├── steps/
│   ├── requirements.yaml          # 에이전트 참조·순서·필수 여부·단계 지침 참조
│   ├── design.yaml
│   ├── implementation.yaml
│   ├── verification.yaml
│   └── review.yaml
├── workflows/
│   ├── standard-feature.yaml      # 위 step 참조
│   └── bugfix.yaml
├── projects/
│   └── commerce/
│       ├── project.yaml           # 논리 프로젝트 ID·workflow·repo 상대 경로
│       ├── instructions.md
│       └── scopes/
│           └── checkout.yaml      # 결제 영역 경로·추가 지침/에이전트 참조
├── schemas/                       # 편집기/CI 검증용 공개 스키마
└── .github/CODEOWNERS
```

이 디렉토리는 제안 형식이다. 프로젝트 정의는 필요한 경우에만 중앙 저장소에 두며 모든 코드/실제 기능 작업을 복사하지 않는다. 공통 에이전트/스텝은 ID로 참조하고 프로젝트마다 복제하지 않는다. 서로 다른 회사는 별도 패키지/워크스페이스로 분리한다. 같은 이름의 에이전트도 package ID + agent ID로 구분한다. 로컬 DB UUID를 공유 식별자로 사용하지 않는다.

회사 기본 역할은 제공되며 사용자가 처음부터 모두 만들 필요가 없다. 템플릿 버전과 사용자 변경 내역을 구분한다. Markdown은 역할·출력 기준을 담고, YAML은 적용 범위·필수 여부·참조·검사 명령을 담는다. 형식은 제한된 안전한 YAML/JSON 스키마로 정하고 코드 실행 태그·임의 평가를 허용하지 않는다.

### 2. 실제 프로젝트 저장소

```text
commerce-app/
├── .roopre/
│   ├── harness.yaml               # 회사 패키지 출처·선택 workflow·허용된 보완
│   ├── harness.lock.json          # 정확한 Git commit·내용 hash·스키마 버전
│   ├── instructions.md            # 이 코드와 함께 변경할 프로젝트 지침
│   └── features/
│       └── FTR-123-checkout/
│           ├── feature.yaml       # 기능 ID·코드 범위·추가 지침/배치 참조
│           ├── requirements.md
│           └── design.md
└── src/
```

중앙의 projects/commerce는 회사에서 배포할 기본값이다. 프로젝트의 .roopre는 코드 변경과 함께 리뷰할 보완/선택 설정이다. 같은 항목을 양쪽에서 암묵적으로 편집하지 않고 Settings에서 출처·수정 권한을 보여준다.

기능별 폴더는 해당 작업의 명세와 설정을 관리하는 단위다. 실시간 실행 로그·산출물·대화·개인 승인 증빙을 회사 표준 저장소에 자동 커밋하지 않는다. 기능 문서의 Git 저장은 앱 내 DB와 연결해 명시적으로 내보내기/적용한다. 가져온 design.md가 존재한다는 이유로 승인 상태를 복원하지 않는다.

### 3. 개인 Mac의 로컬 설정

프로젝트 ID → 실제 checkout 절대 경로, 논리 연결 이름 → 로컬 vault 연결 ID, 로컬 UI 선택과 캐시를 앱 사용자 데이터에 저장한다. API key·토큰·DB 비밀번호·암호화 blob·개인 절대 경로는 export 대상이 아니다. 공유 가능한 모델 요구/논리 연결 이름과 로컬 인증 정보를 분리한다. import 후 누락 연결만 매핑하고 준비되지 않은 실행은 차단한다.

## 디렉토리와 기능 범위

프로젝트는 Git 저장소를 기준으로 식별하고 필요 시 저장소 내부 작업 디렉토리를 지정한다. 실제 checkout 위치는 사용자마다 달라도 된다.

하나의 기능을 한 코드 폴더에 가두지 않는다. 결제 기능은 src/features/checkout/**, src/api/payments/**, tests/e2e/checkout/**를 함께 다룰 수 있다. 기능에는 repo 상대 경로 여러 개를 선언한다. 기존 Node 단일 패키지 실행 지원 범위는 그대로이며 경로 설정 추가만으로 monorepo나 다중 저장소 실행 지원을 선언하지 않는다.

“해당 경로에 적용할 지침”과 “수정할 수 있는 경로”는 별개 설정이다. 경로 지침은 관련 영역 규칙을 선택하며 작업 파일 권한을 자동으로 확대하지 않는다. 범위 밖 변경은 감지 후 승인 계약 재검토를 요구한다. 공유 유틸처럼 미리 몰랐던 수정 범위가 발견되면 에이전트가 몰래 넓히지 않고 변경 제안을 남긴다.

첫 구현은 승인된 기능 범위에 걸리는 규칙을 실행 전에 결정해 스냅샷에 고정한다. 실행 중 읽은 파일에 따라 무제한 지침을 주입하는 동작은 초기 범위에서 제외한다. 교차 영역 작업에는 관련 필수 검사와 검토자를 합쳐야 한다. 겹치는 구조화 설정 충돌은 오류로 표시하고 Markdown의 의미 충돌을 자동 해결했다고 주장하지 않는다.

## 상속·검증 계약

회사 공통 → 프로젝트 → 경로/기능 범위 → 현재 단계 → 현재 에이전트 → 승인된 기능 입력 순서로 출처를 설명한다. 이는 단순히 마지막 설정이 이기는 규칙이 아니다.

- 필수 검사/리뷰는 ID를 기준으로 합치고 하위 범위가 제거하지 못한다.
- 읽기 전용 단계의 쓰기 권한·본인 승인 같은 프로그램 경계는 지침으로 해제하지 못한다.
- 회사가 변경을 허용한 기본값만 프로젝트에서 변경할 수 있다. 명시적인 리스트 교체/추가 구문을 구분한다.
- 수치 제한은 단위와 의미를 검증한다. 예산/시간은 상위가 정한 최대값 안에서 설정하고 기능별 조합을 명확하게 표시한다.
- 사용하지 않은 역할/프로젝트 변경은 관련 없는 실행을 무효화하지 않는다. 실제 참조 집합과 적용 결과 hash를 기록한다.
- import된 검사 명령은 코드를 실행할 수 있으므로 적용 비교에서 명령·환경·권한 변경을 보여주고 기존 실행 프로필 승인에 포함한다. import 자체는 명령을 실행하지 않는다.

## 버전과 설정 원본

Git source → exact commit으로 조회 → 스키마·참조·범위 검증 → 임시 제안 → 차이/영향 확인 → 한 트랜잭션으로 적용 → immutable snapshot → 실행 순서다.

main/latest 또는 이동 가능한 tag만 저장하지 않는다. 표시 버전과 실제 commit/content hash를 모두 lock에 기록한다. 다른 팀원이 같은 패키지/commit·프로젝트 보완 설정을 적용했는지 확인할 수 있어야 한다. 동일 설정이 모델 결과를 동일하게 만든다는 보장은 아니다.

Settings 편집 또는 비서 대화는 로컬 초안을 만든다. 원본 공유 패키지는 읽기 전용 캐시다. 적용은 현재 프로젝트의 보완 설정으로 하거나 표준 저장소에 보낼 파일 변경안으로 내보낸다. 자동 push/PR/merge를 하지 않는다. 공유 표준을 개인 DB에서 몰래 수정한 채 같은 버전으로 표시하지 않는다. 개인 초안·표준과 다름·업데이트 가능·호환 불가를 구분한다.

표준 업데이트가 있으면 변경 비교와 영향 목록을 보여준다. 진행 중 실행은 임의로 새 버전을 읽지 않는다. 초기 정책은 관련 활성 실행이 있으면 적용을 보류하고, 종료 후 최신 revision 재확인 및 필요한 설계 재승인을 거친다. 이전 버전 선택도 새로운 적용 요청으로 남기며 예전 승인 증빙을 부활시키지 않는다.

원격 연결이 끊겨도 이미 검증한 lock/cache로 로컬 실행할 수 있다. 다만 중앙의 최신 필수 버전/폐기 상태를 확인하지 못하면 “회사 최신 기준 확인 불가”로 표시한다. 원격 CI/정책에서 현재 허용 버전인지 따로 검사할 수 있다.

## Import / Export와 Settings UX

권장 첫 범위는 폴더 import/export와 Git URL+ref 연결이다. 앱 배포 ZIP과 별개이며 기본 교환 형식은 사람이 Git diff로 검토할 수 있는 파일이다. 초기에는 한 저장소 안의 참조만 허용하고 임의 원격 중첩 의존성 설치는 지원하지 않는다.

Settings → 하네스:

- 회사 표준 / 프로젝트 / 기능 범위 / 단계 / 에이전트를 탐색하는 트리.
- 선택 항목의 원문·폼 편집과 “실제 적용되는 설정” 탭.
- 각 값 옆 출처·버전·상속·필수 잠금 표시.
- Git source·고정 commit·로컬 변경·업데이트 여부.
- import 미리보기: 새 에이전트, 변경 배치/검사, 누락 연결, 충돌, 영향받는 승인/실행.
- export 범위: 전체 재사용 패키지, 프로젝트 보완, 기능 하네스, 개별 단계/에이전트. 부분 export는 필요한 참조의 폐쇄 집합 또는 명시적인 외부 패키지 의존 목록을 포함해 누락을 감지한다.

폴더 import는 허용 파일/경로·파일 수·크기·스키마 버전·중복 ID·존재하지 않는 참조·순환 참조를 검사한다. 절대 경로·상위 디렉토리 탈출·symlink·특수 파일·프로젝트 경계 밖 참조를 거절한다. Git 가져오기는 실행/설치 hook·submodule·LFS smudge 등 부수 실행을 자동 활성화하지 않는 전용 경로로 설계한다. Git 인증은 기존 OS/Git 자격 증명 경로를 사용하고 URL의 토큰을 설정이나 로그에 저장하지 않는다.

export는 선언된 설정만 포함하는 allowlist 방식으로 구성한다. 비밀처럼 보이는 문자열 경고는 보조 수단이며 임의 Markdown에 사람이 붙여넣은 모든 비밀을 완벽히 탐지한다고 주장하지 않는다. 실행 로그/캐시/대화/승인/환경 인증은 기본 제외한다.

## 팀 운영

표준 변경 → 표준 저장소 PR → 스키마/참조/상속/정책 호환 검사 → 담당자 리뷰 → merge/tag → 앱에서 변경 비교 → 프로젝트 적용 순서다. CODEOWNERS를 두는 것만으로 승인이 강제되지는 않으며 저장소 보호 규칙과 필수 검사 설정이 필요하다. GitHub 지원 요금제/권한을 확인해야 한다. 현재 roopre private 저장소에서 서버 보호가 이미 활성화됐다고 주장하지 않는다.

개발 프로젝트의 CI는 신뢰된 검사 코드와 조직이 허용한 표준 commit/hash를 기준으로 필수 검사/리뷰를 검증해야 한다. PR이 자기 설정/검사기를 바꿔 스스로 통과하게 해서는 안 된다. 로컬 앱이 만든 성공 JSON이나 정책 hash만으로 실제 검사 성공을 신뢰하지 않는다. 팀 전체 강제와 중앙 인증/감사는 후속 별도 구현 범위다.

## 단계별 도입과 인수 기준

1. portable ID·manifest·Markdown·workflow·정책 스키마와 deterministic resolver. 로컬 폴더 round-trip.
2. Settings 트리·유효 설정·변경 비교·로컬 경로/연결 매핑과 원자적 적용.
3. Git exact commit 동기화·lock·업데이트·캐시·되돌리기.
4. 조직 보호/CI 연계, 표준 배포 상태와 비서 설명.

필수 검사: 서로 다른 로컬 경로의 두 사용자 환경에서 같은 effective hash가 나옴(개인 경로/key 제외), export/import 후 의미 보존, 중복 import의 ID 안정성, 부분 실패 시 전체 보존, 중복/순환/탈출 경로 거절, 필수 기준 완화 차단, 현재 실행의 버전 고정, 설정 변경 후 재승인, 원격 중단·stale 적용 거절, 기존 사용자 설정의 명시적 변환 및 원본 보존.

이 검토에서는 코드 변경·새 저장소 생성·Git 게시·팀 설정 배포를 수행하지 않았다. 기존 [전역 비서/기본 에이전트/진행 화면 제안](GLOBAL-ASSISTANT-PROPOSAL.md)의 설정 모델을 이 패키지 계약에 연결하는 방향으로 제안한다.

## 공식 자료와 설계에 적용한 판단

- [Claude Code memory와 경로별 규칙](https://code.claude.com/docs/en/memory): 프로젝트/사용자/조직 범위와 경로별 지침 관리가 있다. 문서는 지침이 모델 문맥이며 강제 설정과 다르다고 명시한다. 루프리는 이를 참고하되 자체 필수 승인/검사 계약을 따로 관리한다. Claude 형식과 루프리 패키지가 완전 호환된다고 주장하지 않는다.
- [GitHub CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners): 파일별 검토 책임을 지정할 수 있다. 하네스 지침/필수 규칙 변경의 리뷰 소유자를 두는 데 적용한다.
- [GitHub ruleset 규칙](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets): 필수 리뷰·상태 검사 등의 서버 측 조건을 구성할 수 있다. Git 공유만으로 팀의 필수 품질 기준이 강제된다고 주장하지 않고, 지원 플랜/권한을 전제로 별도 연계한다.
