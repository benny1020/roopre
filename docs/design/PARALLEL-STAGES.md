# 단계 내부 병렬 실행

사용자 지시: “병렬로하자”, “디폴트를 병렬로”. 같은 단계의 에이전트는 기본 병렬로 실행하고, 단계 간 순서는 유지한다. 단계별로 순차 실행을 선택할 수 있다.

## 실행 계약

- workflow의 `execution`에 단계별 `parallel | sequential`을 저장한다. 새 실행 스냅샷에는 모든 단계의 방식을 고정한다. 필드가 없는 새 workflow는 병렬을 기본으로 해석한다. 이미 저장된 실행 스냅샷에 필드가 없으면 기존 순차 의미를 보존한다.
- 승인 binding에는 실행 의미 버전을 포함한다. 과거 승인을 그대로 사용해 바뀐 병렬 동작을 시작하지 않는다. 실행 방식 변경은 일반 지침 변경처럼 재승인 대상이다.
- 기본 병렬은 동시에 최대 3개씩 실행한다. 각 묶음의 남은 예산을 나누어 예약하므로 모든 에이전트가 같은 잔여 예산을 각각 사용하는 것을 방지한다. CLI 추정 비용 한도의 기존 한계는 유지한다.
- 각 병렬 작업은 독립 clone, 컨테이너, 네트워크, 모델 gateway를 가진다. 단계 시작 시점의 동일한 소스와 입력을 받으며 다른 에이전트의 진행 중 결과를 보지 않는다.
- 전체 단계가 끝난 후 다음 단계로 넘어간다. 프로세스 실패/시간 초과/취소 시 후속 묶음과 단계를 시작하지 않고, 시작한 작업이 정리될 때까지 기다린다.
- 구현 결과는 변경 경로가 겹치지 않을 때 하나의 패치로 통합한다. 파일/디렉터리 충돌은 덮어쓰지 않고 실행을 중단하며 각 작업 공간과 결과를 보존한다. 합친 소스에 기존 보호 파일 검사·고정 검사·독립 리뷰를 수행한다.
- 병렬 요구사항/설계 결과는 각각 구조를 검증하고, 여러 유효 초안은 같은 단계의 첫 유효 에이전트로 별도 통합한다. 통합 작업도 비용·입력·결과를 기록한다. 통합된 초안은 사람의 설계 승인과 별개다.
- 검증/리뷰 결과는 모두 보존한다. 필수 에이전트의 실패를 다른 성공으로 덮지 않는다. 검증 단계와 리뷰 단계는 별도의 barrier를 유지한다.
- 하네스 import/export에 실행 방식을 포함한다. UI에 각 단계의 기본 병렬과 순차 선택, 동시 실행 한도, 순차 선택 시 실행 순서를 표시한다.

## 검증

스케줄러의 병렬 중첩·순차 보존·실패 시 후속 작업 금지, 동일 입력 스냅샷, 독립 변경 통합과 충돌 보존, 승인 무효화와 import/export 왕복을 검사한다. Docker fixture로 실제 동시 컨테이너·연결 격리·중단 정리와 결과 증거를 확인한다. 유료 모델 응답 품질은 별도 미검증 항목이다.
