# 전역 관제 · 판단할 일 · 역할별 운영 맵

작성: 2026-09-28 · 설계 담당: Astra · 구현 담당: GPT-5.6 Terra · 검토 담당: Astra

상태: **사용자 검토용 세부 설계안. 이 문서는 사용자 본인의 설계 승인을 기록하거나 대체하지 않는다.** 사용자의 진행 지시에 따라 구현 전에 검토 가능한 계약을 구체화했다. 기존 버전 승인 기록을 이번 세부 설계의 승인으로 재사용하지 않는다. 제품 구현·검증 완료 문서가 아니다.

## 사용자 검토 요약

전역 관제에서 여러 프로젝트의 현재 단계와 다음 행동을 보고, 판단할 일에서 설계 승인·실패·결과 검토 대상을 찾는다. 역할별 운영 맵은 실제 실행 인스턴스를 역할 그룹으로 보여주는 같은 데이터의 보조 보기다.

주요 흐름은 `범위/검색 선택 → 기능 행 또는 역할 카드 선택 → Inspector에서 이유·담당·근거 확인 → 기존 설계/diff/검증 상세 → 뒤로 가서 원래 필터와 선택 복원`이다. 1024px에서는 Inspector가 목록 아래로 이동한다.

관제에서 승인·실행·재시도를 직접 수행하지 않는다. 사용자 본인의 설계 승인, 고정 검사와 격리 실행은 기존 상세/실행 경로를 유지한다. 화면에는 큐와 실제 작업, 오래된 상태와 정상 확인, 보고된 추정 비용과 미보고 비용이 구분된다.

이번에는 전역 비서, 새 실행기, 예산 강제, 24시간 실행, 팀 인증을 만들지 않는다. 검토 후 확정할 내용은 이 3개 화면의 범위, 복원 위치를 우선하는 기본 진입, 정적인 역할 맵이다. **현재는 세부 설계안이며 사용자 승인 기록은 아직 없다.**

## 1. 요구사항과 범위

확인된 요구는 여러 프로젝트에서 지금 무엇이 실행되고, 무엇을 기다리며, 누가 다음 행동을 해야 하는지 찾는 것이다. 기존 설계 승인·고정 검사·격리 실행·근거 검토 흐름을 유지한다. 전역 화면은 기존 데이터의 읽기 모델과 상세 화면으로의 진입점이다.

| 구분 | 이번 제안                                                                                                                                |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 포함 | 프로젝트×단계 관제, 판단할 일, 역할별 운영 맵, 공통 Inspector, 상태/비용/확인 시점 집계, 기존 상세 이동과 탐색 복원                      |
| 유지 | 본인 OS 인증 설계 승인, 승인 binding, 고정 검사, 독립 clone/컨테이너, 실행 점유 및 종료 확인, 기존 취소·복구·재승인 절차                 |
| 제외 | 전역 비서와 LLM 요약, 새 runner/daemon, 24시간 실행, 기간 예산 강제, 예약/자동 재시도, 팀 인증·회사 권한, 역할 정의·배치 편집, 병합·배포 |
| 금지 | 관제에서 승인/시작/재시도/취소 mutation 수행, 관제 조회가 DB 상태를 변경, 시안 예시를 실제 데이터로 표시                                 |

사용자 결정이 필요한 항목은 마지막 절에 모았다. 아래 수치와 UI 규칙은 구체적인 제안이며 승인이 이미 있었다는 뜻이 아니다.

## 2. 현재 계약과 구현 경계

- `src/shared/contracts.ts`: Snapshot은 projects/features/runs/gates와 revision/sequence/runnerConnected를 제공한다. 전역 관제 전용 서버나 이벤트 스트림은 필요하지 않다.
- `src/shared/runtime.ts`: `activeStatuses`에 queued가 포함된다. 이 배열 길이를 실제 실행 수로 사용하지 않는다. `costUsd`는 run 누적 추정이며 `costReported`는 보고값 존재 여부다.
- `src/shared/harness.ts`: 정의/배치와 `AgentExecution`은 다르다. 실행에는 id, assignmentId, revision, stage, model, attempt, startedAt/endedAt이 있다.
- `src/runner/manager.ts`: 실행 한도는 워크스페이스 정책으로 관리한다. 기본값은 전역 3개 run, 프로젝트당 2개 run, 단계 내부 3개 작업이며 순차 단계에는 1개씩 실행된다. 종료 미확인 run은 점유를 유지한다.
- `src/renderer/src/App.tsx`: 기존 약 1초 순차 snapshot 조회를 재사용한다. 보기마다 추가 polling을 만들지 않는다. revision 역행 거부와 설정 문맥 복원을 보존한다.
- `workspace/navigation.ts`, `useNavigationHistory.ts`: scope/selected/query/settingsContext/runtimeSection과 뒤로/앞으로 이력을 확장한다. 단순히 새 페이지로 보내고 기존 문맥을 초기화하지 않는다.

새 파일 제안은 `workspace/portfolio-model.ts`(React 없는 순수 projection), `PortfolioOverview.tsx`, `AttentionQueue.tsx`, `AgentOperationsMap.tsx`, `WorkInspector.tsx`다. 실제 분할은 Terra가 책임 응집도에 맞게 조정할 수 있다. Node/main/database import는 renderer에 추가하지 않는다. 읽기 모델은 기존 Snapshot과 클라이언트 조회 상태만 입력받는다. 이번 범위에서는 DB 스키마·IPC·runner 명령을 바꾸지 않는다.

## 3. 입력 → 집계 → 표시 계약

입력은 `(snapshot, lastSuccessfulFetchAt, fetchError, now, viewState)`다. 같은 입력은 같은 projection을 만든다. 시간 판정은 주입된 now를 사용해 검사 가능하게 한다. 결과는 기능 행, run 집계, 실제 에이전트 인스턴스, 판단 항목, 선택 상세로 구성한다.

공통 참조는 `{projectId, featureId, runId?, attempt?, agentExecutionId?}`다. 실행 근거에는 반드시 runId와 attempt를 붙인다. 행 선택과 상세 진입은 별개이며 Inspector 선택만으로 기존 기능 화면이 열리지는 않는다.

### 3.1 최신 실행과 과거 실행

기능의 대표 run은 현재 저장 계약에 맞춰 `snapshot.runs`에서 해당 기능의 마지막 항목을 사용한다. 현재 `workState`와 같은 규칙이며 재조회 시 배열을 이름/상태로 재정렬한 결과를 최신으로 쓰지 않는다. `runtime.attempt`가 존재하면 그것을 현재 시도로 사용한다. runtime이 없는 fixture/과거 run은 실제 runner 집계에서 제외하고 `실행 정보 없음`으로 구분한다.

기능 행은 최신 run을 보여주되, 전역 점유/종료 미확인 집계는 **모든 run**을 검사한다. 최신 run으로 과거 run의 미확인 점유를 숨기면 안 된다. 사용자가 과거 run을 선택하면 자동으로 최신 run으로 바꾸지 않고 `과거 실행`과 시도를 명시한다. 현재 근거에는 현재 attempt의 evidence/agents/artifacts만 포함한다. 기록이 없으면 과거 통과를 재사용하지 않는다.

### 3.2 수치의 정확한 의미

| 수치             | 계산 및 표시                                                                                                                                        |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 큐 대기          | runtime이 있고 status=queued인 run 수. 실제 작업 중에 더하지 않는다                                                                                 |
| 작업 진행 기록   | preparing/implementing/verifying/reviewing/repairing인 runtime run. preparing은 `환경 준비`로 분리 설명                                             |
| 기록상 슬롯 점유 | runtime의 terminationConfirmed=false 또는 queued 외 active 상태인 run의 합집합. 종료 미확인 포함                                                    |
| 종료 확인 중     | terminal 상태인데 terminationConfirmed=false인 run. 재실행 가능/슬롯 해제로 표시하지 않는다                                                         |
| 에이전트 작업 중 | 현재 attempt의 status=running인 AgentExecution, 부모 run도 non-queued active이며 cancelRequested가 아니고 조회·heartbeat 최신일 때만 실제 활성 표시 |
| 역할 정의/배치   | 별도 참고 숫자로만 제공. 에이전트 작업 중 수와 합산하지 않음                                                                                        |

run 점유와 에이전트 수는 다른 분모다. `기록상 슬롯 점유 2/3 · 큐 1 · 에이전트 작업 중 4`처럼 현재 실행 정책의 전역 한도를 함께 표시한다. 프로젝트에는 `동시 run 최대 2개`, 단계 상세에는 `최대 3개 / 순차면 1개`를 설명한다. 필터된 결과의 수치는 `선택 범위`로 표시하고 전역 점유의 분모를 프로젝트 필터에 따라 바꾸지 않는다. 한도를 초과하는 기록이 발견되면 잘라내지 않고 불일치로 표시한다.

runner는 메모리 `active` Map도 점유에 포함하므로 snapshot만으로 순간 점유를 완전히 알 수 없다. 따라서 `남은 슬롯이 있으니 실행 가능`이라는 보증, 확정 큐 순위, 시작 예정 시각은 제공하지 않는다. 큐 이유는 동일 프로젝트 점유/전역 한도와 일치할 때 `기록상 … 대기`로 설명하고 나머지는 `실행기 확인 대기`로 둔다. 승인 유효성과 실제 claim은 기존 runner가 판단한다.

### 3.3 에이전트 정체성

맵 key는 `runId + attempt + AgentExecution.id`다. 이름·역할명·definition ID로 실행을 합치지 않는다. 표시 이름/모델/지침 revision은 실행 당시 AgentExecution 또는 해당 run의 resolved harness에서 읽는다. 현재 라이브러리의 최신 revision으로 과거 실행을 덮어쓰지 않는다. assignmentId로 resolved harness를 참조할 수 없으면 정의 ID를 추측하지 않는다.

같은 정의의 두 실행은 두 카드이며, 정의만 있고 실행 기록이 없으면 활성 카드를 만들지 않는다. queued run의 배치 계획도 활성 카드로 만들지 않는다. 기존 executionGraph의 executing 판정을 그대로 활성 집계로 재사용하지 않는다. 취소 요청 중이면 정상 작업 중 대신 `중단 요청 처리 중`이며 점유는 종료 확인까지 남긴다. 부모가 종료됐는데 running 기록이 남으면 `종료된 run의 잔여 기록`으로 Inspector에서 확인하고 활성 수에서 제외한다. 상태가 오래됐으면 `마지막 기록: 실행 중 · 현재 확인 불가`로 표시하며 마지막 알려진 인스턴스를 숨기지 않는다.

### 3.4 최신성·연결·진전

`lastSuccessfulFetchAt`(채택한 snapshot의 조회 성공 시각), `runtime.heartbeat`(runner 기록), 최근 event 시각(활동 기록)을 별도로 표시한다. heartbeat가 최신이라는 이유로 검사 통과·의미 있는 진전·agent별 생존을 주장하지 않는다. 에이전트별 heartbeat는 현재 계약에 없다. 낮은 revision 응답은 버리고 조회 성공 시각도 갱신하지 않는다. 동일 revision 성공은 정지한 workspace의 정상 조회일 수 있으므로 시각을 갱신한다. 수송 연결 성공과 표시 데이터의 최신성을 구분한다. 현재 App.refresh의 lastSync는 거부된 응답에도 갱신될 수 있으므로 관제에 그대로 전달하지 않고 이 채택 조건에 맞춘다.

제안 임계값: 마지막 조회가 5초를 넘으면 `오래된 화면`, 조회 실패 또는 runnerConnected=false이면 `연결 확인 필요`; 활성 run heartbeat가 30초를 넘으면 `실행 상태 확인 필요`. heartbeat 누락/잘못된 날짜/현재보다 5초 이상 미래 시각은 `알 수 없음`이다. 정상 heartbeat 간격은 현재 10초다. queued/terminal에는 heartbeat 나이로 실행 장애를 판정하지 않는다.

오래되거나 실패한 조회에서도 마지막 snapshot은 남기되 정상 실시간 색상/애니메이션을 제거하고 마지막 성공 시각을 표시한다. now는 snapshot 응답과 독립된 가벼운 UI timer로 갱신하여 조회 promise가 끝나지 않아도 freshness가 나빠져야 한다. 이를 위해 추가 polling을 만들지 않는다. 다시 연결되면 완전 snapshot을 받아 최신성 조건을 모두 만족한 경우에만 해제한다. 단순 연결 이벤트로 정상 복구 처리하지 않는다. 이 임계값은 UI 신뢰도 분류이며 자동 취소/재시작 정책이 아니다.

### 3.5 비용

선택 범위에 속하는 **모든 runtime run의 costUsd를 run ID당 한 번** 합산한다. 최신 run만 합산하거나 같은 run의 attempt별로 중복 합산하지 않는다. 기간 필터가 없으므로 `현재 저장 기록의 보고된 누적 추정 $…`로 표시한다. attempt별·에이전트별 비용은 현재 데이터로 계산할 수 없다.

costReported=true이고 costUsd가 유효한 경우만 보고값에 포함한다. false/undefined는 `비용 미보고 N개 run`; 무효 숫자는 `비용 정보 오류`다. 유효하게 보고된 0만 0으로 표시한다. 일부라도 미보고이면 총액에 `일부`를 붙이며 완전한 총비용으로 설명하지 않는다. costReported=true도 CLI 호출 일부만 보고됐을 수 있으므로 `완전 보고`나 실제 청구액으로 표현하지 않는다. 보고 run 수/미보고 run 수를 함께 제공한다. 예산 잔액·절대 지출 상한은 계산하지 않는다.

## 4. 관제와 판단할 일

기본 구성은 범위/검색/보기 전환 → 상태 요약 → 판단할 일 → 프로젝트×단계 → Inspector다. 단계는 현재 제품의 5개 축(요구사항, 설계, 구현, 검증, 결과 검토)을 유지한다. 검증 셀 내부에서 고정 검사와 AI 리뷰를 구분한다. 시안의 6열은 실행 단계 스키마 변경의 근거가 아니다. 현재 단계보다 왼쪽이라는 이유만으로 체크 표시를 만들지 않는다. 해당 설계·승인·동일 시도 근거가 있을 때만 완료 표식을 쓰고, 계획 초안 completed를 개발 완료로 표시하지 않는다.

적용 기준/버전은 실제 resolved harness와 근거의 값만 쓰고 없으면 `미기록`이다. 시안의 역할 라이브러리/팀 개발 표준은 기존 에이전트/하네스 메뉴를 재사용하며 별도 메뉴 개편으로 확장하지 않는다.

프로젝트 그룹은 접을 수 있고 기능 행은 제목, 상태, 현재 동작, 다음 담당/행동을 제공한다. Inspector는 동일 ref에 대해 프로젝트/기능, 현재 및 과거 구분, run/attempt, 상태 근거, 적용 설계/정책, 확인 시점, 비용 보고 상태, 다음 담당과 상세 링크를 제공한다. event message는 `최근 기록`으로 라벨링하고 확인되지 않은 현재 수행 작업으로 단정하지 않는다.

판단할 일은 이벤트 수신함이 아니라 현재 snapshot에서 유도한 행동 목록이다. 읽음/읽지 않음이나 영구 삭제 상태를 추가하지 않는다. 중복 key는 `{featureId, runId?, attempt?, reasonCode}`이며 조회를 반복해도 같은 항목이 늘어나지 않는다. 이유가 해결된 완전 snapshot을 받으면 제거한다. 기능 하나에 독립된 두 문제가 있으면 숨기지 않되 상단 `판단할 기능 N개`와 목록 `사유 M개`를 구분한다.

| 근거                                   | 다음 담당                | 행동/이동                                                           |
| -------------------------------------- | ------------------------ | ------------------------------------------------------------------- |
| gate=in_review                         | 사람(본인)               | 설계와 승인 조건 보기 → 기존 설계 상세                              |
| changes_requested 또는 blocking thread | 사람(본인)               | 차단 의견·수정 요청 보기                                            |
| gate.eligible이며 run 없음             | 사람(본인)               | 개발 준비 상태. 판단 경고가 아닌 준비 항목; 기존 실행 설정으로 이동 |
| failed/interrupted                     | 사람(본인)               | 실패 근거·복구 조건 보기. 자동 재시도 없음                          |
| blocked 또는 현재 승인 무효 근거       | 사람(본인)               | 승인/정책 변경 조건 확인                                            |
| ready_for_merge                        | 사람(본인)               | 변경·검증·리뷰 결과 보기. 완료/병합 처리하지 않음                   |
| 종료 미확인                            | 시스템; 환경 복구는 사람 | 종료 확인 상태와 기존 복구 안내 보기                                |
| 조회/heartbeat 확인 불가               | 시스템; 연결 확인은 사람 | 연결 상태·마지막 근거 보기                                          |
| queued/환경 준비/고정 검사             | 시스템                   | 실행기 판정 대기, 실제 기록에 근거한 대기 이유                      |
| 최신 실제 agent 작업                   | 해당 실행 인스턴스       | 역할명·프로젝트·기능과 결과 대기                                    |

근거가 없으면 `담당 확인 필요`/`상세에서 확인`으로 남기고 특정 사람·AI에게 임의 할당하지 않는다. 환경 문제는 전역 배너 한 개로도 표시하되 개별 run의 고유 문제를 대체하지 않는다. 긴급도는 종료/상태 확인 필요 → 실패/차단 → 사용자 설계/결과 검토 순으로 제안한다. polling이 행 순서와 포커스를 재배치하지 않게 기존 항목 순서를 유지하고 새 항목은 같은 그룹 끝에 추가한다.

## 5. 역할별 운영 맵

동일 projection/필터/선택을 사용하는 보조 보기다. 요구사항·설계/구현/검증/리뷰의 역할 그룹 안에 실제 실행 카드를 배치한다. run의 resolved 단계와 AgentExecution.stage로 그룹화하고 사용자 역할 이름은 카드에 그대로 보인다. 정적인 그리드를 우선하며 자유 좌표, 조직 계층, 장식 선, 캐릭터 애니메이션은 추가하지 않는다.

카드는 역할 이름, 프로젝트/기능, 단계, run/attempt, 실행 당시 모델, 상태·확인 시점으로 구분한다. 현재 활성 기록이 없으면 `현재 실행 기록 없음`이며 역할 정의 없음과 구분한다. stale 인스턴스는 별도 상태 문구로 남긴다. 표에서 선택한 기능이 맵에 실행 카드가 없더라도 `이 기능의 활성 실행 없음` Inspector를 유지한다. 맵에서 선택한 agent는 표로 돌아가도 같은 기능/run/attempt 문맥을 보존한다.

## 6. 탐색·반응형·접근성

기본 진입 제안: 복원할 유효한 위치가 없고 프로젝트가 2개 이상이면 전역 관제, 1개면 그 프로젝트 기능 보기, 0개면 기존 온보딩. 저장된 기존 작업 위치는 프로젝트 수 변화로 강제 이동하지 않는다. 기존 실행 현황은 과거 run을 찾아 여는 경로로 유지한다.

전역 문맥 `{projectScope, query, statusFilter, view, selectionRef, collapsedProjectIds, scrollAnchor}`를 기존 WorkspaceLocation에 선택 필드로 추가하는 방식을 권장한다. `scope=portfolio`와 Inspector selection은 기존 `selected=featureId` 상세 진입과 분리한다. 검색 입력은 이력 항목을 매 키마다 생성하지 않는다. 명시적인 보기/상세 이동은 이력에 남기고 복원 시 최신 snapshot으로 ref 유효성을 검사한다. 삭제된 대상은 다른 run으로 조용히 대체하지 않고 사라짐 안내 후 상위 범위로 이동한다.

기능 상세의 설계/diff/검증/실행 이력으로 가는 링크는 정확한 feature/run/attempt를 전달한다. 기존 화면이 attempt 직접 선택을 지원하지 않으면 해당 run을 열고 과거 시도임을 안내한다. 뒤로/앞으로는 범위·필터·보기·Inspector·스크롤을 복원한다. 신규 관제 scope는 navigation validator, sidebar, command palette 모두에 반영한다. 설정 화면 A→B→뒤로/앞으로에서는 child form의 프로젝트와 실제 mutation 대상까지 일치해야 한다. 기존 navigationRestore 재진입 경계와 시작 시 선택 기능 복원을 보존한다. 기존 설계 편집 초안/설정 초안을 polling이나 보기 전환으로 초기화하지 않는다.

1440px에서는 관제와 약 280px Inspector를 나란히 배치한다. **1024px에서는 Inspector를 선택 행 아래 또는 목록 아래에 배치**하고 페이지 자체 가로 넘침을 없앤다. 표가 넓으면 이름/현재 상태/다음 행동을 먼저 보여주고 상세 단계는 내부 스크롤 가능한 영역으로 한정한다. 텍스트 축소로 전체를 끼워 맞추지 않는다. 긴 프로젝트·역할·기능명은 줄바꿈 또는 상세 전체 읽기를 제공한다. 라이트/다크 기존 토큰을 사용한다.

행/카드는 native button 또는 명확한 링크이며 Enter/Space로 선택, 상세 링크로 진입한다. 선택 상태와 focus-visible을 구분한다. 접기는 aria-expanded, 보기 전환은 aria-pressed, 상태는 색+문구로 전달한다. Inspector 갱신 때 강제 focus 이동을 하지 않는다. 사용자가 상세로 이동/복귀하면 진입 버튼으로 focus를 복원한다. 매초 live region 공지를 하지 않고 연결 실패/복구 등 의미 있는 변화만 polite로 알린다. 기존 Cmd/Ctrl+[ ]·검색·모달 키보드 규칙을 보존한다.

| 상황                | 표시와 동작                                                                  |
| ------------------- | ---------------------------------------------------------------------------- |
| 최초 loading        | 제목/골격과 `불러오는 중`; 0개/정상 상태 수치 미표시                         |
| 최초 fetch 실패     | 오류·조회 재시도, 실행 mutation 없음                                         |
| 이후 fetch 실패     | 마지막 데이터+시각+stale 배너, 정상 실시간 표시 해제                         |
| 프로젝트 없음       | 기존 프로젝트 준비 경로                                                      |
| 기능/실행 없음      | 각각 구별한 안내와 기존 설계 경로                                            |
| 검색/필터 결과 없음 | 필터 해제 버튼, 숨겨진 다른 기능 Inspector 표시 금지                         |
| 선택이 필터 밖      | 선택 ref는 복원용 보존, Inspector는 `현재 필터 밖`으로 숨기고 해제 경로 제공 |
| 부분 관계 누락      | 유실 ref를 오류로 표시하고 유효한 다른 행은 유지; 활성 카드/근거 조작 금지   |

## 7. 완료 기준과 검증 계획

아래 검사는 구현 후 수행할 조건이다. 이 문서 작성으로 통과한 것이 아니다.

| AC              | 재현 조건과 통과 기준                                                                                                                                                                                                                                                                                             |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AC-01 집계      | 3개 프로젝트에 실행 2, 큐 1, 준비/종료 미확인 사례를 구성. queued를 실제 실행에 더하지 않으며 전역 2/프로젝트 1/단계 3을 다른 한도로 설명                                                                                                                                                                         |
| AC-02 보존 점유 | 최신 run 외 과거 run에 종료 미확인 기록을 배치. 점유와 확인 대상에서 빠지지 않고 남은 슬롯/실행 가능을 확정하지 않음. nonterminal cancelRequested run은 중단 요청/종료 확인 표시, 슬롯 유지, 활성 agent 수 제외                                                                                                   |
| AC-03 시도      | 한 run의 1차 통과·2차 실패 및 다른 run의 결과를 혼합. 현재 행/Inspector의 검사·artifact·agent에 현재 attempt만 사용; 과거 선택은 명시적으로 유지                                                                                                                                                                  |
| AC-04 정체성    | 같은 역할 이름/definition을 두 프로젝트 실행에 사용하고 정의 revision 변경. 두 인스턴스를 보존하며 실행 당시 모델/revision을 표시                                                                                                                                                                                 |
| AC-05 비용      | 보고된 0, 양수, 미보고, 일부 보고, 다중 attempt를 구성. run당 1회 합산, 미보고를 0으로 표시하지 않고 비용 완전성/청구 확정을 주장하지 않음                                                                                                                                                                        |
| AC-06 최신성    | 5초 조회 경계, 30초 heartbeat 경계, 누락/미래/잘못된 시각, 조회 오류/재연결. 오래된 녹색 활성 제거, 마지막 데이터 보존, 새 snapshot 전 정상 복귀 없음. 미완료 조회 promise도 시간 경과로 stale 전환. out-of-order 낮은 revision 응답은 화면/freshness 모두 갱신하지 않고 동일 revision 정상 응답은 조회 시각 갱신 |
| AC-07 판단      | 승인/실패/차단/결과/종료 확인별 다음 담당·행동·정확한 근거 링크가 있고 해결 snapshot에서 제거. 링크는 올바른 feature/run과 목적에 맞는 실제 존재 상세 탭(설계/검증/실행 등)을 선택. 조회 반복 중 중복 항목/자동 실행 없음                                                                                         |

| AC-10 권한      | 관제에서 보기/필터/선택/상세 이동을 수행하며 IPC/명령 spy로 승인·시작·재시도·취소 등 mutation 호출 0 확인. 상세 승인은 기존 본인 OS 인증/도메인 경로만 사용                                                                                                                                                       |
| AC-11 회귀      | 기존 승인 binding·취소·검사·실행 격리·설정 문맥·run 선택·diff/근거 테스트 기대값을 약화하지 않고 통과                                                                                                                                                                                                             |
| AC-12 native    | Electron에서 실제 snapshot 기반 전역→상세→뒤로, DB 조회 실패/복구, 앱 재진입의 문맥 확인. Web fixture 통과와 native 검증을 별도로 보고                                                                                                                                                                            |

검사 배치는 순수 projection 회귀 `tests/portfolio.test.ts`(제안), 기존 `tests/web/ade.spec.ts` 또는 전용 관제 spec, navigation의 기존 unit 회귀를 확장한다. 기존 ade spec의 prepare는 첫 기능 execution을 자동 선택하므로 관제 전용 준비 함수 또는 명시적 관제 이동을 사용한다. 상태/비용/권한 경계 중심으로 검사하고 단순 문구나 구현 구조를 그대로 복제하는 테스트는 피한다.

필수 실행: `pnpm check`, `pnpm test:web`, `pnpm test:desktop`, `pnpm check:mac`. `test:desktop` 기존 결과만으로 AC-12가 충족됐다고 하지 않는다. 관제 native smoke 또는 통합 회귀를 추가해 실제 Electron 경로를 확인한다. `check:mac`은 앱 패키지 무결성이며 실제 본인 인증 성공이나 모델 실행 증거가 아니다. 실제 사용자의 인증을 fixture로 합성하지 않는다. OS 인증 직접 검증이 필요하면 사용자 본인이 수행하며 수행 여부를 별도 기록한다.

이번 설계대로 runner/domain을 수정하지 않으면 비용을 발생시키는 실모델 실행은 요구하지 않는다. 구현 중 그 경계를 바꿔야 하면 범위를 다시 검토하고 해당 runner/resilience/parallel 통합 검사를 추가한다. 환경 때문에 native 검사가 불가능하면 `미검증` 사유와 남은 AC를 명시하며 완료로 보고하지 않는다. 릴리스/PR 검증 근거는 실제 명령·exit code·대상 head·화면 증거·미실행 범위를 `docs/VERIFICATION.md`에 남긴다.

구현 완료 뒤 Astra 독립 리뷰는 정확한 head/base에서 수행하고 저장소 PR 절차를 따른다. 사용자 설계 승인은 AI 리뷰가 대체하지 않는다. PR 머지는 최신 사용자 지시인 `머지는 너가 승인하면 알아서 머지해`의 위임 범위에서 독립 리뷰, 최신 CI, 정확한 head 확인 후 진행한다. 기존 검사 실패를 숨기거나 기대값 완화로 통과시키지 않는다.

## 8. 사용자 검토 대상

위 3개 화면과 공통 Inspector, `복원 위치 우선, 새 위치는 다중 프로젝트 관제 / 단일 프로젝트 기능` 기본 진입, 정적인 역할 그룹 카드를 **하나의 세부 설계안**으로 검토한다. 세 가지를 각각 별도 질문으로 재확인할 필요는 없다. 비서/실행기 변경은 후속 범위다.

최신성 5초/30초, 비용 누적 기준, 직접 승인 없는 상세 이동, 1024px 레이아웃 및 AC를 포함한 본 문서가 검토 대상이다. 승인 시 사용자 원문·범위·날짜를 별도 승인 기록에 남긴 뒤 Terra 구현, Astra 리뷰로 진행한다. 문서의 상태는 그 전까지 제안으로 유지한다.

## Terra 구현 핸드오프

사용자 승인 기록이 마련되면 승인된 문서 버전과 AC를 먼저 고정한다. 이어 순수 projection과 의미 경계 회귀 → 공통 Inspector/전역 관제 → 판단할 일 → 역할 맵 → 탐색/반응형 통합 → 필수 검사/native 증거 순서로 구현한다. 화면마다 독자적인 집계나 polling을 만들지 않는다. 문서의 기능 단계/실제 역할 구분을 시안의 예시 숫자나 체크 표시로 대체하지 않는다.

각 체크포인트에는 변경 파일, 충족 AC, 실행 명령과 결과, 남은 불확실성을 남긴다. runner/IPC/DB 변경 필요 또는 승인 의미 변경이 발견되면 이번 설계의 범위를 넘어갔음을 표시하고 설계 검토로 돌린다. 마지막 산출물은 구현 diff, 검사 증거, 미검증 목록, Astra 독립 리뷰에 필요한 정확한 head/base다. 사용자 승인을 대신 생성하거나 문서 상태를 임의로 승인으로 바꾸지 않는다.
